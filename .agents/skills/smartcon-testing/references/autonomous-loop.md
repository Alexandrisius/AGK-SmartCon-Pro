# Автономная разработка: петля «тест ↔ лог ↔ фикс»

> Методика автономной разработки DB-уровня SmartCon: агент пишет код,
> гоняет интеграционные тесты в реальном Revit, читает `smartcon.log`,
> чинит баги и повторяет до критерия выхода — без человека в цикле.
> Собрано из практик closed-loop agent control (AWS Builder Center),
> tests-first loop, anti-reward-hacking и нашего опыта #104.

## Когда петля работает, а когда нет

| Работает (замкнуто в петле) | НЕ работает (нужен ручной тест) |
|---|---|
| Вся граница SmartCon ↔ Revit API: транзакции, типы, параметры, сегменты, материалы, структуры, ExtensibleStorage, коллекторы | WPF/UI: панели, меню, диалоги, контекстные меню, бейджи |
| Импорт/экспорт, staging, хэши, миграции БД | DnD-жесты, размещение, PickObjects |
| Детерминированная логика sync/update | Модальные диалоги реальной UI-сессии (в headless-хосте поведение другое: silent rollback vs modal) |
| Регрессии существующего поведения | Freeze панели, focus, balloon |

**Гейт петли:** «все интеграционные тесты зелёные + лог чистый».
**Гейт фичи:** петля + один ручной UI-прогон (для UI-кода — обязателен).

## Контракт петли (перед стартом)

Перед запуском автономного цикла зафиксируй письменно (в промпте/плане):

1. **Objective** — что должно работать (одна фича/баг, не «улучши модуль»).
2. **Acceptance criteria — машинно-проверяемые:**
   - какие тесты (новые/существующие) должны быть зелёными;
   - какие контрактные строки должны появиться в логе (`Type 'X': Updated, N parameters written`), каких не должно быть (`[ERR]`, необъяснимых `[WRN]`);
   - граница наблюдения: состояние документа после операции (не «код написан»).
3. **Constraints** — что нельзя менять (FHV3 хэш, public API, другие модули).
4. **Iteration cap** — максимум итераций фикса одного и того же (обычно 3).

## Команды цикла

```bash
# Точечный прогон (быстрый, для итераций фикса)
dotnet run --project src/SmartCon.IntegrationTests -c Debug.R25 --framework net8.0-windows -- --treenode-filter "/*/*/MyClassTests/*"

# Полный гейт (обязателен перед коммитом). RevitVersion = любой УСТАНОВЛЕННЫЙ
# net48-Revit (2021–2024): суть прогона — платформа net48, а не конкретный год.
# R27 (net10) — когда установлен Revit 2027; три платформы: net48/net8/net10.
dotnet run --project src/SmartCon.IntegrationTests -c Debug.R25 --framework net8.0-windows
dotnet run --project src/SmartCon.IntegrationTests -c Debug.R21 --framework net48 -p:RevitVersion=2023
dotnet run --project src/SmartCon.IntegrationTests -c Debug.R27 --framework net10.0-windows

# Лог цикла
Select-String "$env:APPDATA\AGK\SmartCon\smartcon.log" -Encoding UTF8 -Pattern "\[ERR\]|\[WRN\]"
```

## Правила петли (нарушение = расхождение с реальностью)

1. **Тесты — контракт, не мишень.** Когда тест падает — чинится production-код.
   Исключение: тест ошибочно кодирует предположение (наш кейс: «Type Mark пуст»,
   а шаблонный тип имеет значение). Тогда меняем тест, НО только после того,
   как лог/зонд доказал, что поведение production-кода корректно.
2. **Fix the code, not the test** — второе правило из AWS closed-loop control.
3. **Лог — authoritative record, не самооценка агента.** «Сделано» =
   зелёный сьют + чистый лог, а не «я думаю, что работает».
4. **Не гадай — зондируй.** Не понял причину за 2-3 итерации →
   [паттерн «зонд»](integration-testing.md#паттерн-зонд--диагностика-поведения-revit-вместо-гипотез)
   (измерь реальность вместо гипотезы) или Exa (3+ запроса). Стоп-кран AGENTS.md.
5. **Один баг — одна итерация.** Мелкие коммиты на зелёном состоянии;
   не накапливать 3 несвязных фикса в одном diff.
6. **Seed проверяй результатом.** `Set` может молча вернуть `false`,
   `get_Parameter` — `null`. Сид, который не сработал, измеряет не тот
   сценарий (кейс wrapping-параметров #104).
7. **Машино-зависимость — в assert контракта.** Revit отклоняет операцию
   разными способами на разных машинах (upfront exception vs silent
   rollback). Assert формулируй как контракт (`threw || !committed`),
   не как конкретный механизм.

## Стоп-условия (границы автономии)

| Условие | Действие |
|---|---|
| Сьют зелёный + лог чистый + acceptance criteria выполнены | СТОП: коммит + gate general-валидатором. Не изобретать доработки (starvation gate) |
| 3 итерации подряд та же ошибка без изменений | СТОП: зонд / Exa / вопрос пользователю |
| Ошибка невоспроизводима в тест-хосте (modal, UI) | СТОП: сценарий для ручного теста пользователем |
| Падения появились в несвязанных тестах | СТОП: регрессия в чужом коде — откатить/изолировать свой diff |
| Нужен запретный файл (docs/, ADR до подтверждения) | СТОП: дождаться подтверждения пользователя |

## Финал цикла (обязательная последовательность)

1. Полный сьют R25 + net48 (+R27, когда установлен Revit 2027) — зелёный.
2. Все 6 shipping-конфигураций сборки (R19/R21/R24/R25/R26/R27) — 0/0.
3. Лог: нет `[ERR]`, необъяснимых `[WRN]`; контрактные строки присутствуют; цепочки `OpId` целые.
4. Коммит (атомарный, с `Refs #N`).
5. **Adversarial review**: gate general-субагентом со свежим контекстом (diff + критерии + инварианты) — аналог cross-model review из практик; агент не судит свой код сам.
6. UI-фича → сценарий ручного теста пользователю с ожидаемыми строками лога.
7. Только после подтверждения: docs/ADR/changelog/issues.

## Типовые провалы петли (и как их избегать)

- **Reward hacking**: тест переписан под неверный код → правило 1-2 + adversarial review.
- **Flaky feedback**: тест зелёный через раз → карантин и расследование, НЕ «прогнал ещё раз до зелёного».
- **Loop drift**: длинная петля уходит от цели → короткие циклы с коммитом, периодическое перечитывание acceptance criteria.
- **Silent scope creep**: «заодно поправлю ещё вон там» → constraints из контракта; лишнее — отдельной задачей.
