# Бизнес-план: уход от temp-логики в модуле Family Manager

---

## 1. Общее описание

**Суть изменения.** Перестроить pipeline импорта семейств так, чтобы между «источником данных» (файл на диске пользователя, активный документ Revit, выделенные элементы) и «managed-хранилищем каталога» не было промежуточной temp-папки с дубликатами файлов.

**Проблема текущего решения.** Перед показом batch-диалога мы копируем (или создаём заново) каждый файл во временную папку, чтобы получить к нему доступ для: (а) вычисления SHA-256, (б) определения размера файла, (в) показа в диалоге статуса «Дубликат». Это создаёт избыточные операции ввода-вывода, временный мусор, дополнительные сервисы очистки и точку отказа при нехватке места / прав доступа к temp-папке.

**Целевая аудитория.** MEP-инженер, который импортирует семейства в локальный каталог. Не меняется.

**Что упрощается в UX.**
- В batch-диалоге больше нет колонки «Размер файла».
- В batch-диалоге больше нет статуса «Дубликат» — все семейства с тем же нормализованным именем всегда идут как новая версия (vN+1) или перезапись текущей версии.
- Действие «Skip» остаётся только осознанным выбором пользователя (а не навязанным правилом).

**Что НЕ упрощается в UX.**
- Batch-диалог остаётся — пользователь по-прежнему видит список, выбирает категорию, подтверждает.
- Версионирование сохраняется — новая версия семейства = отдельная папка в managed-хранилище.
- Read-only-флаг на managed-файлах сохраняется (защита от случайной перезаписи).

**Главное бизнес-преимущество.** Pipeline становится линейным: «источник → метаданные → подтверждение → managed-хранилище». Никаких промежуточных копий, никакой очистки мусора, меньше движущихся частей.

## 2. Цепочка Use Case

### UC-1. Импорт файла семейства с диска (основной сценарий)

| Поле | Описание |
|---|---|
| **Актор** | MEP-инженер |
| **Предусловие** | В проводнике выбран один или несколько `.rfa`-файлов. Каталог SmartCon Family Manager открыт. |
| **Контекст** | Пользователь получил семейства от коллеги / скачал с сайта производителя / имеет свою библиотеку и хочет добавить их в локальный каталог. |
| **Действие** | 1) Пользователь нажимает «Импорт файлов» и выбирает `.rfa` файлы в стандартном диалоге Windows. 2) Система читает метаданные каждого файла напрямую (без копирования куда-либо): имя, версия Revit, нормализованное имя для проверки дубликатов. 3) Система сопоставляет каждое имя с каталогом: «Новое» или «Существующее (можно сделать новую версию)». 4) Система показывает batch-диалог со списком файлов, статусом, выбором категории и действия. 5) Пользователь подтверждает или правит. 6) Система открывает каждый файл с диска пользователя, извлекает типы и параметры, сохраняет копию в managed-хранилище как новую версию (или обновление текущей — по выбору пользователя). 7) Дерево каталога обновляется. |
| **Результат** | Все одобренные файлы появились в каталоге как новые или обновлённые версии существующих семейств. Исходные файлы на диске пользователя не тронуты. |
| **Критерий успеха** | — В каталоге появились записи для всех одобренных файлов. — Для существующих имён создана новая версия (vN+1) или обновлена текущая — по выбору пользователя. — Исходные `.rfa` на диске пользователя имеют ту же дату/размер, что и до импорта. — Никаких файлов во временной папке не создавалось. |
| **Альтернативные сценарии** | (а) Файл повреждён / не читается → строка в диалоге помечается «Ошибка», импорт пропускается. (б) Пользователь отменяет диалог → ничего не импортируется, исходные файлы не тронуты. (в) Импорт прерван (сбой Revit) → частично импортированные остаются в каталоге, остальные не импортируются, пользователь видит отчёт. |

| Поле | Описание |
|---|---|
| **Актор** | MEP-инженер |
| **Предусловие** | В Revit открыт `.rfa` документ. Каталог SmartCon открыт. |
| **Контекст** | Пользователь только что отредактировал семейство через команду «Редактировать» (см. UC-5) или работает с семейством в обычном режиме и хочет добавить его в каталог как новую версию. |

| **Альтернативные сценарии** | (а) Активный документ — `.rvt` проект, а не `.rfa` → см. UC-3. (б) Семейство с таким именем уже есть в каталоге → пользователь выбирает «Новая версия» или «Обновить текущую». |

### UC-3. Импорт активного проекта (`.rvt` открыт в Revit)

| Поле | Описание |
|---|---|
| **Актор** | MEP-инженер |
| **Предусловие** | В Revit открыт `.rvt` проект. Каталог SmartCon открыт. |
| **Контекст** | Пользователь хочет «вытащить» все уникальные семейства из текущего проекта в каталог: и системные категории (воздуховоды, трубы, и т.д.), и загружаемые семейства (фитинги, арматура, оборудование). |
| **Действие** | 1) Пользователь нажимает «Импорт активного файла» (или «Импорт проекта» — если команда раздельная). 2) Система анализирует активный проект: находит все размещённые системные категории и все уникальные загружаемые семейства. 3) Система показывает сводное подтверждение: «Будет импортировано: 5 системных категорий (47 типов), 23 загружаемых семейства. Продолжить?». 4) После подтверждения система показывает batch-диалог со списком: имя, тип (системное/loadable), категория, статус по нормализованному имени. 5) Пользователь правит категории / действия, подтверждает. 6) Система для каждой системной категории создаёт минимальный проект с этими типами (напрямую в managed-хранилище, не в temp) и сохраняет как новую версию. 7) Для каждого loadable семейства открывает семейство в режиме редактирования и сохраняет копию в managed-хранилище как новую версию. |
| **Результат** | Все одобренные семейства проекта добавлены в каталог. |
| **Критерий успеха** | — В каталоге появились записи для всех одобренных системных категорий и loadable семейств. — Активный проект в Revit не изменён (никакие элементы не удалены, размер файла не изменился). — Никаких файлов во временной папке не создавалось. |
| **Альтернативные сценарии** | (а) Системная категория с таким именем уже есть → пользователь выбирает «Новая версия». (б) Loadable семейство не размещено, а загружено → всё равно попадает в список (если не настроена фильтрация). (в) Пользователь хочет импортировать только системные / только loadable → предусмотреть фильтр в batch-диалоге. |

## 3. Ограничения и допущения

**Бизнес-ограничения**
- Источник `.rfa` файла — всегда локальная файловая система пользователя (не сетевые диски с ограниченным доступом). Допущение разумное: даже сейчас сценарий сетевого импорта не поддерживается.
- В batch-диалоге остаётся возможность переопределить категорию для каждой строки. Без этого пользователи не смогут исправлять ошибки классификации.
- Версионирование семейств сохраняется в полном объёме. Никакая «оптимизация» хранения версий не входит в скоуп.
- Read-only-флаг на managed-файлах сохраняется (защита от случайной перезаписи через проводник).

**Допущения о пользователях**
- Пользователь понимает, что такое «новая версия» vs «обновление текущей версии» (это уже знакомое поведение).
- Пользователь готов явно выбрать действие в batch-диалоге (отсутствие автоматического определения дубликатов требует чуть больше внимания).
- Пользователь работает в одиночку с локальным каталогом (нет сценария «два человека одновременно редактируют одну версию»).

**Внешние зависимости**
- Поведение Revit при «Открыть документ» для read-only файла: пользователь сможет редактировать, но «Сохранить» будет недоступно — только «Сохранить как». Это документированное поведение Revit.
- Для создания минимального проекта (системные категории) всё ещё требуется доступ к шаблону проекта Revit. Это не temp-логика, это часть бизнес-процесса импорта системной категории.

**Технические зависимости (выходят за рамки бизнес-плана, но фиксирую для контекста)**
- Размер `FamilyBatchImportItem` уменьшится (нет `FileSizeBytes`, нет `Sha256`).
- Из схемы данных (если есть) удаляются поля `sha256`, `size_bytes` (или делаются nullable + неиспользуемые для обратной совместимости).

## 4. Что НЕ входит в скоуп

- **Удаление старых версий семейств** (UI «удалить версию v1, оставить v3») — отдельная фича, не блокируется этим рефакторингом.
- **Изменение схемы хранения managed-файлов** — структура папок `{catalogItemId}\{versionLabel}\{name}.rfa` остаётся.

- **Оптимизация извлечения типов и параметров** (открытие/закрытие Revit-документа) — отдельная задача, рефакторинг не должен её затрагивать.
- **Поддержка сетевых папок и облачных хранилищ** как источника импорта — нет в скоупе.
- **Многопользовательский режим с блокировками** — нет в скоупе.
- **Миграция данных существующих каталогов** (если в БД остались `sha256` от старых импортов) — допущение: миграция «заполнить null, не удалять колонку» или «оставить как есть, перестать использовать». Решение принимается на этапе планирования.

## Резюме оценки идеи

**Идея сильная.** Удаление промежуточной temp-логики — это упрощение без потери функциональности для пользователя (всё, что ему было нужно — он видел в batch-диалоге; большая часть данных там была «для красоты»).

**Главный выигрыш:**
- Удаляется один сервис очистки + один файл констант путей.
- Удаляется один класс «подготовки активного файла» (или сильно упрощается).
- Удаляется фаза копирования/создания файлов перед диалогом — это самая дорогая по времени и рискам часть.
- Упрощается модель данных batch-строки (нет SHA256, нет размера).

**Главный проигрыш:**
- Теряется автоматическое определение дубликатов по содержимому. Это редкий, но реальный сценарий: пользователь получил два разных `.rfa` с одинаковым именем от разных людей. # Бизнес-план v2: уход от temp-логики в модуле Family Manager

> **Изменения относительно v1:** UC-2 переработан (активный документ не открывается заново, работаем с ним in-place через `FamilyManager`); все UC упрощены с учётом ответов пользователя; явно зафиксировано breaking change v2.0.0.

---

## 1. Общее описание

**Суть изменения.** Перестроить pipeline импорта семейств так, чтобы между «источником данных» (файл на диске пользователя, активный документ Revit, выделенные элементы) и «managed-хранилищем каталога» не было промежуточной temp-папки с дубликатами файлов и не было сервиса очистки этой папки.

**Проблема текущего решения.** Перед показом batch-диалога (или непосредственно при импорте) мы копируем / создаём каждый файл во временной папке `%TEMP%\SmartCon\...`, чтобы получить к нему доступ для вычисления SHA-256, определения размера файла, показа статуса «Дубликат», а также чтобы безопасно открыть файл через Revit API (открытие уже открытого файла в Revit запрещено). Это создаёт избыточные операции ввода-вывода, временный мусор, дополнительные сервисы очистки и точку отказа при нехватке места / прав доступа к temp-папке.

**Что удаляется из системы (полностью, безвозвратно в v2.0.0):**
- Временная папка `%TEMP%\SmartCon\FMLoad` — больше не создаётся.
- Временная папка `%TEMP%\SmartCon\SystemFamilyLoadFromProject` — больше не создаётся.
- Сервис очистки временных файлов.
- Файл констант путей для временных папок.
- Класс подготовки активного `.rfa` (логика `SaveAs` в temp + копирование sidecar).
- Колонка «Размер файла» в batch-диалоге.
- Колонка / статус «Дубликат» в batch-диалоге.
- Данные SHA-256 в batch-строке (поле исчезает).
- Данные о размере файла в batch-строке (поле исчегает).

**Версия 2.0.0 — breaking change.** Это большое архитектурное изменение. Старые базы каталогов (если в них остались записи с `sha256` / `size_bytes`) переносятся без миграции данных — колонки остаются в схеме, но более не заполняются. Существующие managed-файлы в каталоге пользователя остаются как есть, не требуют пересохранения.

**Целевая аудитория.** MEP-инженер, который импортирует семейства в локальный каталог. Не меняется.

### UC-1. Импорт файла семейства с диска (основной сценарий)

|---|---|
| **Актор** | MEP-инженер |
| **Предусловие** | В проводнике выбран один или несколько `.rfa`-файлов. Каталог SmartCon Family Manager открыт. |
| **Контекст** | Пользователь получил семейства от коллеги / скачал с сайта производителя / имеет свою библиотеку и хочет добавить их в локальный каталог. |

### UC-2. Импорт активного `.rfa` семейства

| Поле | Описание |
|---|---|
| **Актор** | MEP-инженер |
| **Предусловие** | В Revit открыт `.rfa` документ (например, после команды «Редактировать» — UC-5 — или просто как самостоятельный файл). |
| **Контекст** | Пользователь только что отредактировал семейство и хочет сохранить его в каталог как новую версию. **Ключевое отличие от UC-1:** активный документ **уже открыт** в Revit, и его не нужно заново открывать для извлечения типов. |
| **Действие** | 1) Пользователь нажимает «Импорт активного файла». 2) Система читает метаданные активного `.rfa` (имя, версия Revit, нормализованное имя) — без копирования файла куда-либо. 3) Система показывает batch-диалог с одной строкой и предзаполненным действием «Новая версия» (или «Обновить текущую», если семейство с таким именем уже есть в каталоге). 4) После подтверждения: (a) если есть `.txt` рядом с активным файлом — система применяет типы из Type Catalog в активный документ через `FamilyManager` (это легитимная модификация активного документа, на которую пользователь дал согласие кнопкой «Импорт»); (b) система сохраняет активный документ в managed-хранилище через `SaveAs(managedRfaPath)`; (c) система открывает сохранённую managed-копию через `OpenDocumentFile` (это уже **отдельный** документ, не активный) для извлечения типов, параметров, общих вложенных семейств; (d) сохраняет данные в БД; (e) закрывает открытую managed-копию. 5) Активный документ остаётся открытым в Revit в том состоянии, в котором его оставил пользователь (с применёнными типами из `.txt`, если был). |
| **Результат** | Активное семейство добавлено в каталог как новая версия. Пользователь продолжает работать в Revit с тем же открытым документом. |
| **Критерий успеха** | — В каталоге появилась запись с новой версией семейства. — Активный документ в Revit **не закрыт** и **не перезаписан** в исходное место (исходный файл пользователя на диске остался без изменений). — Никаких файлов во временной папке не создавалось. — Если был `.txt` — типы из каталога применены и в активный документ, и в managed-копию. |
| **Альтернативные сценарии** | (а) Активный документ — `.rvt` проект, а не `.rfa` → см. UC-3. (б) Семейство с таким именем уже есть в каталоге → пользователь выбирает «Новая версия» (по умолчанию) или «Обновить текущую» или «Пропустить». (в) Активный документ только что открыт из managed-хранилища и имеет read-only-флаг на уровне ОС (от UC-5) → `FamilyManager` всё равно может читать типы и параметры, но модификация (применение `.txt`) потребует снятия read-only с managed-копии перед `SaveAs`. Это деталь реализации, в UX не вылезает. (г) `.txt` есть, но активный документ read-only (только что из managed) → пользователь видит предупреждение «Type Catalog не применён (файл read-only)» и предложение либо сохранить копию к себе, либо пропустить. |

| Поле | Описание |

## 3. Ограничения и допущения

**Бизнес-ограничения**
- Источник `.rfa`-файла — всегда локальная файловая система пользователя. Допущение разумное: даже сейчас сценарий сетевого импорта не поддерживается.
- В batch-диалоге остаётся возможность переопределить категорию для каждой строки. Без этого пользователи не смогут исправлять ошибки классификации.
- Версионирование семейств сохраняется в полном объёме. Никакая «оптимизация» хранения версий не входит в скоуп.
- Read-only-флаг на managed-файлах сохраняется на уровне ОС (защита от случайной перезаписи через проводник). Это **не мешает** Revit'у открыть файл для редактирования — Revit при открытии read-only файла сообщает об этом, но не блокирует работу в памяти. «Сохранить» будет недоступно, «Сохранить как» — работает.
- В batch-диалоге **не появляются** статусы «Дубликат» (удалён) и «Ошибка чтения SHA-256» (удалён). Остаётся: «Новое», «Существующее», «Ошибка чтения файла» (новая формулировка).

**Допущения о пользователях**
- Пользователь понимает, что «Новая версия» и «Обновить текущую» — это разные действия с разными последствиями (vN+1 vs перезапись vN).
- Пользователь готов явно выбрать действие в batch-диалоге (отсутствие автоматического определения дубликатов по содержимому требует чуть больше внимания).
- Пользователь работает в одиночку с локальным каталогом.

**Архитектурные допущения (зафиксированы для ясности, в скоуп не входят)**
- Active document `.rfa` остаётся в памяти Revit, мы работаем с ним через `FamilyManager` (чтение / модификация).
- Для `OpenDocumentFile` после `SaveAs` в managed — managed-копия должна быть **отдельным** документом (не active), чтобы не нарушить работу пользователя в Revit.
- `SaveAs` в managed для активного `.rfa` **модифицирует** активный документ в части `PathName` (Revit перерисует заголовок окна). Это ожидаемое поведение, на которое пользователь дал согласие кнопкой «Импорт».

**Внешние зависимости**
- Поведение Revit при «Открыть документ» для read-only файла: пользователь может редактировать в памяти, «Сохранить» недоступно, «Сохранить как» работает. Подтверждено в Revit API docs.
- `FamilyManager` API в активном документе работает без необходимости `OpenDocumentFile` — подтверждено в Revit API docs (методы `.Types`, `.Parameters`, `.CurrentType`).
- `OpenDocumentFile` на уже открытом файле **запрещён** Revit'ом (исключение «file is opened by another Revit instance»). Подтверждено в Autodesk community.
- Для создания минимального проекта (системные категории) требуется доступ к шаблону проекта Revit. Это не temp-логика, это часть бизнес-процесса импорта системной категории.

**Схема данных**
- Колонки `sha256` и `size_bytes` остаются в таблице `family_files` (если там были) — НЕ удаляются и НЕ обнуляются, просто перестают заполняться при импорте. Это сохраняет обратную совместимость со старыми каталогами.
- В batch-строке поля `FileSizeBytes` и `Sha256` удаляются полностью (это UI-модель, не схема БД).

## Резюме оценки идеи (обновлённое)

**Идея сильная, реализуемая.** Исследование кода и Revit API подтвердило, что temp-логика существует не «для красоты», а по жёстким причинам:
- `OpenDocumentFile` на уже открытом файле в Revit запрещён → нужна копия, чтобы открыть.
- Активный документ нельзя закрывать / перезаписывать в исходный путь → нужна копия.
- SHA-256 и размер файла — единственное, что действительно требует наличия физического файла **до** диалога. После отказа от этих данных — файл до диалога больше не нужен.

**Главный выигрыш архитектуры:**
- Удаляется один сервис очистки.
- Удаляется один файл констант путей.
- Удаляется класс подготовки активного файла (или сильно упрощается).
- Удаляется фаза копирования / создания файлов перед диалогом.
- Упрощается модель данных batch-строки (нет SHA-256, нет размера).
- Упрощается UC-2: активный документ **не закрывается** и **не открывается заново** — работаем с ним in-place через `FamilyManager`.

**Главный проигрыш (принят пользователем):**
- Теряется автоматическое определение дубликатов по содержимому. Если пользователь получил два разных `.rfa` с одинаковым именем от разных людей — обе загрузятся как версии vN+1 и vN+2 одного семейства. **Компенсация:** в batch-диалоге остаётся отображение «существующая версия v3 от 2026-06-15, 12 типов» — пользователь визуально сравнивает.

**Готовность к реализации: 9/10.** Все вопросы закрыты, технические детали описаны, остаётся одно: передать в plan-режим для проектирования миграции, схемы и этапности.

**Вариант B (консервативный):** Оставить `ActiveFamilyFilePreparer`, но переделать его — `SaveAs` идёт в managed storage напрямую.

### 6.2. Переделка ImportActiveFileAsync (case Family)

**Файл:** `src/SmartCon.FamilyManager/ViewModels/FamilyManagerMainViewModel.FamilyEdit.cs`

**Стратегия:** вместо `SaveAs(tempRfaPath)` → использовать `SaveAs(managedRfaPath)`. Это означает:
1. Сгенерировать GUID для `catalogItemId` / `fileId` / `versionId` ДО открытия диалога? **Нет** — мы не знаем, отменит ли пользователь. Поэтому:
2. Стратегия: **сначала показать диалог, ПОТОМ создавать managed-файл**. Но это требует знать `catalogItemId` до импорта, что невозможно (нужно узнать, новый это item или existing).

**Решение:** создаём **виртуальную метаданную запись** для batch-диалога (как и для UC-3/UC-4), а реальное `SaveAs` в managed делаем только после подтверждения.

**Алгоритм case Family после рефакторинга:**

1. Получить активный документ через `_awaitableEvent.RaiseAsync` (UI thread).
2. Проверить `IsFamilyDocument`. Если нет → `case Project` (или `None`).
3. Извлечь метаданные: `FileName` (из `activeDoc.Title` или `PathName`), `RevitMajorVersion` (через `IRevitFileInfoReader.ReadRevitVersion` НЕ работает для открытого документа, берём `CurrentRevitVersion`).
4. Lookup в каталоге по `normalizedName`:
   - Если найден → `Status = Existing`, `Action = IncrementVersion` (default), доступен `OverwriteCurrent`.
   - Если не найден → `Status = New`, `Action = IncrementVersion`.
5. Создать **виртуальный** `FamilyBatchImportItem` (без `FilePath`! `FilePath = null` или `"<active-document>"` placeholder).
6. Показать batch dialog с одной строкой.
7. При подтверждении:
   - Если `Action = Skip` или `toImport.Count == 0` → выходим без изменений. **Активный документ остаётся открытым.**
   - Иначе:
     - Сгенерировать GUIDs.
     - Вычислить `managedRfaPath`.
     - **Если есть `.txt` рядом с `activeDoc.PathName`**:
       - Если активный документ **не read-only**: bake в активный документ через `FamilyManager` + `SaveAs(managedRfaPath)`.
       - Если read-only: пропустить bake (показать warning), просто `SaveAs(managedRfaPath)`.
     - **Если нет `.txt`**: `SaveAs(managedRfaPath)` напрямую.
     - `OpenDocumentFile(managedRfaPath)` для извлечения типов/параметров/shared nested.
     - Сохранить данные в БД через `LocalFamilyImportService.ImportFileAsync` / `UpdateFamilyAsync` (но они должны принимать `filePath` = managed path).
     - Закрыть `managedRfaPath` документ.
     - **Активный документ пользователя остаётся открытым** (его `PathName` теперь указывает на managed path, что нормально).

**Проблема:** текущий `ImportFileAsync` сам делает `SaveAs(managedRfaPath)` внутри. Нужно переделать либо:
- **Вариант A:** Передать `activeDoc` в `ImportFileAsync` через `FamilyImportRequest.SourceDocument` (ref/document handle).
- **Вариант B:** `ImportFileAsync` принимает `sourceFilePath` — но тогда для UC-2 он не подходит (source = active doc, а не файл).
- **Вариант C (рекомендуется):** Создать новый метод `ImportActiveFamilyAsync(FamilyImportRequest request, Document activeDoc, ...)` в `IFamilyImportService` — отдельный flow для активного документа.

**Решение:** ввести `IFamilyImportService.ImportActiveFamilyAsync`:

```csharp
Task<FamilyImportResult> ImportActiveFamilyAsync(
    Document activeDoc,                     // активный документ (уже открыт)
    string catalogItemId,                   // null = new, не null = existing
    string? existingVersionLabel,           // для IncrementVersion
    FamilyBatchImportAction action,         // IncrementVersion / OverwriteCurrent
    string? categoryId,
    CancellationToken ct = default);
```

Внутри:
- Если `catalogItemId == null` → создаём новый item.
- Если `action == OverwriteCurrent` → перезаписываем текущую версию.
- Если `action == IncrementVersion` → создаём vN+1.
- `SaveAs(managedRfaPath)` напрямую.
- `OpenDocumentFile(managedRfaPath)` для извлечения типов.
- Сохраняем в БД.

**Файл:** `src/SmartCon.Core/Services/Interfaces/IFamilyImportService.cs`

- Добавить метод `ImportActiveFamilyAsync` (см. сигнатуру выше).

**Файл:** `src/SmartCon.FamilyManager/Services/LocalCatalog/LocalFamilyImportService.cs`

### 7.3. Переделка BuildActiveProjectBatchItemsCoreAsync (виртуальные метаданные)

**Файл:** `src/SmartCon.FamilyManager/ViewModels/FamilyManagerMainViewModel.Import.cs`

**Стратегия:** batch items формируются БЕЗ создания реальных файлов. Только метаданные (имя, категория, статус по normalized_name). Файлы создаются **только после подтверждения пользователя** в диалоге.

**Алгоритм:**

1. Анализ: `AnalyzeActiveProject` (без файлов) + `LoadableFamilyScanner.GetUniqueFamilies` (без файлов) — остаётся как есть.
2. Lookup в каталоге:
   - Для каждой системной категории: `FindByNormalizedNameAsync(normalizedName)` → `Existing` или `New`.
   - Для каждого loadable: то же самое.
3. Создать `FamilyBatchImportItem` для каждой записи **БЕЗ** реального файла:
   - `FilePath` = `null` или placeholder (`"system://OST_Pipes"` / `"loadable://{familyName}"`).
   - `FileName` = `displayName` (для system) или `familyName` (для loadable).
   - `Status` = `Existing` или `New`.
   - `TypeCount` = ... (нужно узнать — для system сейчас это `pending.Types.Count` после `AnalyzeActiveProject`, для loadable — `loadable.TypeCount`).
4. Показать batch dialog.
5. После подтверждения:
   - Для каждой одобренной system category:
     - Вычислить `managedRvtPath`.
     - Вызвать `_systemFamilyIsolationProject.CreateCleanProjectWithTypesAndInstancesAsync(activeDoc, uniqueIds, category, displayName, managedRvtPath, ct)`.
     - Передать `managedRvtPath` в `IFamilyImportService.ImportFileAsync` (новый метод `ImportManagedRvtAsync` или доработать существующий `ImportFileAsync` чтобы принимал уже managed path).
   - Для каждого одобренного loadable:
     - Вычислить `managedRfaPath`.
     - Вызвать `StageLoadableFamilyFromProject(info, managedRfaPath)`.
     - Передать в `IFamilyImportService.ImportFileAsync`.

**Проблема:** текущий `ImportFileAsync` сам делает `PrepareManagedRfaAsync` (копирование / bake). Для UC-3/UC-4 файл уже создан в managed — нам нужна только запись в БД (без повторного copy).

**Решение:** ввести `IFamilyImportService.ImportManagedFileAsync`:

```csharp
Task<FamilyImportResult> ImportManagedFileAsync(
    string managedFilePath,           // уже в managed storage
    string fileName,
    int revitMajorVersion,
    FamilyBatchImportAction action,
    string? categoryId,
    string? existingCatalogItemId,
    string? existingVersionLabel,
    CancellationToken ct = default);
```

Внутри:
- `BeginTransaction`.
- INSERT/UPDATE в `family_files`, `catalog_items`, `catalog_versions` (БЕЗ sha256/size_bytes).
- COMMIT.
- Extraction phase: `OpenDocumentFile(managedFilePath)` + извлечение типов/параметров/shared nested.

# Технический план v2.0.0: рефакторинг Family Manager — уход от temp-логики

> **Версия:** 2.0.0 (breaking change)
> **Цель:** Удалить temp-инфраструктуру, упростить pipeline, убрать SHA256/size_bytes/статус "Дубликат".

## Главные принципы

1. **Никаких костылей и временных решений** — это enterprise-решение для open-source проекта, которым будут пользоваться профи.
2. **Breaking change разрешён** — пользователи обновляются до v2.0.0 и применяют миграцию.

## Фаза 13. БД: миграция v14 — DROP COLUMN

### 13.1. Цель миграции

В **существующей БД** пользователя удалить ненужные колонки:
- `family_files.sha256` (TEXT NOT NULL)
- `family_files.size_bytes` (INTEGER NOT NULL)
- `catalog_versions.sha256` (TEXT NOT NULL)

И связанные индексы:
- `ix_family_files_sha256`
- `ix_catalog_versions_sha256`

**Что происходит:** при первом запуске v2.0.0 на БД версии 13 — миграция v14 применяется автоматически. Старая БД обновляется на месте. Никаких новых файлов, никакого side-by-side, никаких UX-диалогов. Пользователь продолжает работать как раньше, но схема упрощена.

### 13.2. SQL-операции (внутри одной транзакции)

```sql
BEGIN IMMEDIATE;

-- 1. Drop indexes (idempotent)
DROP INDEX IF EXISTS ix_family_files_sha256;
DROP INDEX IF EXISTS ix_catalog_versions_sha256;

-- 2. Drop columns (SQLite 3.35+)
ALTER TABLE family_files DROP COLUMN sha256;
ALTER TABLE family_files DROP COLUMN size_bytes;
ALTER TABLE catalog_versions DROP COLUMN sha256;

-- 3. Bump version
UPDATE schema_info SET value = '14' WHERE key = 'schema_version';

COMMIT;
```

# Часть 6. Глоссарий ключевых концепций

## Концепция: Активный документ vs Managed файл

Это **главная концепция**, которую нужно понять для рефакторинга:

### Активный документ (activeDoc)
- Это `Document` в **оперативной памяти Revit** (не файл на диске).
- Доступен через `uiApp.ActiveUIDocument.Document` (только на Revit UI thread).
- У него есть `Title` (обрезанное имя) и `PathName` (полный путь, может быть пустым для untitled).
- **`SaveAs(newPath)` мутирует `PathName`** — после вызова `activeDoc.PathName == newPath`.
- Если пользователь закрывает Revit — документ пропадает из памяти.
- **Read-only флаг на диске** (например, наш managed-файл открыт через "Редактировать") **не мешает** работе с документом в памяти: можно читать типы/параметры через `FamilyManager`, можно делать `SaveAs` в новый путь. Нельзя только `Save` (Ctrl+S).

### Managed файл
- Это `.rfa` файл **на диске** в `%APPDATA%\SmartCon\FamilyManager\default\files\{itemId}\{version}\`.
- Создаётся через `File.Copy` (без Type Catalog) или через baker `SaveAs` (с Type Catalog bake-in).
- **Всегда read-only** (защита от случайной модификации из проводника/IDE).
- Структура: `<db-root>/files/<catalogItemId>/<versionLabel>/<sanitizedName>.rfa`.
- **.txt файла рядом НЕТ** (ADR-033 — bake-in создаёт типы прямо в .rfa).
