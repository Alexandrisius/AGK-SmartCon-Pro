## 1. История: три попытки, один итог

| Попытка | Ветка | Подход | Вердикт |
|---|---|---|---|
| v8 «PGCK» | `floor-heating` | ScalarField + Morse complex + CoverageStateGraph + MILP-solver | **Полный провал.** Построили «забор из вертикальных полос» вместо спирали. ~3000 строк ядра бесполезны. Coverage ~5%. |
| GOTK v2.0 MVP | `floor-heating-v2` (попытка 2) | Реализация методички v2.0 сразу широким фронтом (17 фикстур × 3 паттерна) | **Диагностически успешна, продуктово провальна.** FAIL=10, PARTIAL=31, PASS=0. Тесты были слабые (midpoint-check) → пропустили диагональные мосты и self-intersection. |
| Stage-1/2 revised | `floor-heating-v2` (текущий HEAD) | Узкий scope: Spiral на 5 фикстурах, затем DoubleLoop Variant C | **Лучший результат.** Spiral работает. DoubleLoop работает, кроме известного 44-mm hot-spot на угловых срезах (§5). 78/83 теста зелёные; 5 падающих — ровно эта известная проблема. |

**Главный вывод истории:** рабочим всегда был и остаётся **оригинальный Python-скрипт** (Dynamo, автор неизвестен). Он генерирует спиральные улитки по областям маскировки (FilledRegion) точно и надёжно. Все наши провалы — от отхода от его механики или от попыток «сделать грамотнее» без понимания его ключевых приёмов.

**Мета-уроки (дорого купленные):**

1. **POC перед архитектурой.** 50 строк: Clipper2 offset квадрата → 3 кольца → SVG → перемычки. Только потом — слои, интерфейсы, ядро.
2. **Acceptance criteria = спецификация.** Слабый тест (проверка midpoint сегмента) пропускает заглушку физически. Тесты должны быть написаны так, чтобы заглушка **не могла** их пройти.
3. **Scope creep убивает.** 17 фикстур × 3 паттерна в первой попытке → все компоненты упрощены → ни один не работает. 5 фикстур × 1 паттерн — реалистично.
4. **Громкий провал > тихий мусор.** `CoreResult.Failure` с понятной причиной ценнее, чем красивая SVG с неправильной геометрией.
5. **Классифицируй: баг реализации vs ограничение архитектуры.** Второе не чинится кодом — только сменой спецификации (см. §5).

## 2. Эталон: оригинальный Python-скрипт (единственное, что работает в проде)

Файл-источник: `warm_floor.py` (Dynamo, Revit API). Вход: **FilledRegion с одним контуром**, подающая и обратная труба, шаг, фаска, реверс. Выход: трубы + отводы + отчёт длин.

### 2.1. Пайплайн

```
FilledRegion.GetBoundaries() → SortCurves (нормализация направления обхода)
→ CreateOffsetCurves (кольца через кровельный хак)
→ главный цикл: Shot + угловая компенсация (met=1,3,4,5)
→ сборка точек → RebuildLoop (склейка коллинеарных)
→ DoubleLoop: CurveLoop.CreateViaOffset(loop, offset/2) + midpoint-мост
→ AttachSupply к трубам → Champfer по острым углам
→ Pipe.Create + NewElbowFitting (ClosestConnectors)
```

### 2.2. Кровельный хак (CreateOffsetCurves) — как получаются кольца

В Dynamo нет 2D-offset, поэтому автор строит **временную кровлю** с уклоном 1:1 (45°) по контуру и сечёт её горизонтальными плоскостями:

1. `NewFootPrintRoof(curveArray, level, roofType, ...)`; всем границам `ROOF_CURVE_IS_SLOPE_DEFINING=1`, `ROOF_SLOPE=1`.
2. Наклонные грани при уклоне 1:1 дают: горизонтальное сечение на высоте `z` = линия, параллельная стене, на расстоянии `z − minz`. Это физическая эмуляция Minkowski erosion.
3. Сечения: `zz = minz + offset/2`, затем шаг `offset` до `maxz`. Каждое сечение `CutWithHalfSpace` → грани с нормалью ≈ +Z → `GetEdgesAsCurveLoops` → трансляция на `baseZ`.
4. Кровля удаляется.

**Для C# это не нужно вообще** — Clipper2 `InflatePaths(paths, -delta, JoinType.Miter, EndType.Polygon)` делает то же самое честно (§4.2).

### 2.3. Shot (лучевая стыковка колец)

- Луч `Line(point, point + vector·1000)`.
- Режим 1: если угол между `vector` и направлением к началу сегмента < 1° → кандидат = начало сегмента.
- Режим 2 (fallback): `ComputeClosestPoints(ray, curve)`; принять если distance < 0.001 и параметр не на самом конце сегмента.
- Из кандидатов — ближайший по параметру на луче; кольцо циклически сдвигается, чтобы обход начинался с точки попадания.
- Допуск стыковки: `startPoint.DistanceTo(shotPoint) ≤ 5·offset`, иначе — fallback-ветка с обрезанием предыдущего кольца.

### 2.4. Угловая компенсация (сердце алгоритма)

Перед стыковкой кольцо модифицируется, чтобы расстояние до следующего витка было ровно `offset`:

```
θ₁ = угол(последний сегмент, первый);  θ₂ = угол(первый, второй)
leftOffset  = offset / sin(θ₁)   (если θ₁ < π, иначе offset)
rightOffset = offset / sin(θ₂)   (если θ₂ < π, иначе offset)
```

4 случая по положению точки входа `parameter` на первом сегменте длиной `firstLen`:

| Case (met) | Условие | Действие |
|---|---|---|
| 1 (A) | `parameter < 2·leftOffset` | Первый сегмент от shotPoint; последний укоротить на leftOffset |
| 3 (B) | `parameter ≤ firstLen − rightOffset` | Первый от shotPoint; добавить перемычку от конца кольца к точке «сзади» shotPoint на `offset` (экстраполяция `Evaluate(-offset)`) |
| 4 (C) | конец, `θ₂ < π` | Первый укоротить на rightOffset; циклический сдвиг влево |
| 5 (D) | конец, `θ₂ ≥ π` | Второй укоротить на leftOffset; циклический сдвиг влево |

**Guard (исправление бага v16):** при `|sin(θ)| ≤ 0.01` — fallback `offset` вместо деления на ноль.

### 2.5. DoubleLoop (улитка с подачей и обраткой)

```
loop1 = supply spiral (замкнутый CurveLoop через PolyCurve.ByJoinedCurves)
loop2 = CurveLoop.CreateViaOffset(loop1, offset/2, +Z)   // mitered offset!
p1 = конец loop1; p2 = конец loop2; p3 = (p1+p2)/2        // midpoint
line1 = p1→p3; line2 = p3→p2                              // центральный U-мост
loop2.reverse() + реверс каждого сегмента
inLines  = loop1 + [line1]        // подача
outLines = [line2] + loop2        // обратка
```

### 2.6. Семантика шага (важно, все путаются)

- Пользователь вводит **расстояние между осями соседних труб** `d_user` (напр. 200 мм).
- Код: `offset = d_user · 2` (внутренний шаг между осями колец).
- Обратка строится offset'ом на `offset/2 = d_user` от подачи.
- Итог: `dist(Outer_k, Inner_k) = d_user`, `dist(Inner_k, Outer_{k+1}) = d_user` — везде ровно шаг пользователя.

### 2.7. Фаска (Champfer)

```
θ = угол(l1.dir, −l2.dir);  если θ < π/2 − 0.05:
y = |(x/2) / sin(θ/2)|;  применить если 0 < y < len(l1)/2 и y < len(l2)/2
→ заменить угол на 3 сегмента (укороченный, скос, укороченный)
```

### 2.8. Известные баги оригинала (не переносить!)

| Баг | Суть | Последствие |
|---|---|---|
| `type == Arc` | Проверка встроенного имени `type` вместо `type1` | Дуговая склейка в RebuildLoop никогда не работает |
| `5000` без перевода | `distance − offset > 5000` в футах (~1.5 км) | Проверка дальности подводки почти всегда ложна |
| Асимметрия leftOffset | `angle1 < π and angle2 != 0` (должно быть `angle1 != 0`) | Редкие неправильные leftOffset |
| `PruneDuplicates(points, 10)` | 10 **футов** ≈ 3 м допуск | Может сожрать мелкие детали контура |
| Первый Level/RoofType | Берётся `[0]` из коллектора | Скрытая зависимость от состава проекта |
| `vector = XYZ(0,0,1)` старт | Луч вдоль Z в плоской задаче | Бессмысленно; маскируется fallback'ом |
| `except: pass` | Повсеместно | Молчаливые обрывы спирали, неподключённая обратка, разрывы вместо отводов |
| Multi-contour FilledRegion | Возвращает ошибку | Holes/препятствия не поддержаны вообще |
| `round(res.Distance/10)` | Квантизация выбора сегмента до ~3 м | Необъяснимая эвристика fallback-обрезания |

**Что забираем:** саму схему `Offset → Shot → Step → Pattern`, угловую компенсацию, midpoint-мост DoubleLoop, Chamfer-формулу, `ClosestConnectors` для отводов.
**Что выбрасываем:** кровельный хак (→ Clipper2), все баги, молчаливые except.

## 4. Геометрическое ядро (GOTK) — что доказано рабочим

### 4.1. Пайплайн

```
D_work = Erode(boundary, c_wall + D_tube/2)  ∖  Dilate(obstacle_i, c_obs + D_tube/2)
rings:  R_0 = ∂D_work;  R_{k+1} = Offset(R_k, −d₀)  до VANISH (пусто) или SPLIT (2+ компоненты)
spiral: Shot → угловая компенсация → обход кольца → Step-перемычка (≈ d₀) → следующее кольцо
pattern: Spiral (supply-half) | DoubleLoop (улитка = supply + return + 3 моста)
```

### 4.2. Clipper2 — боевые факты (C#)

- NuGet `Clipper2` (сборка `Clipper2Lib`, namespace `Clipper2Lib`), Boost License, netstandard2.0 → работает и на net48, и на net8.
- **Всегда `PathsD`** (double, мм) с `precision = 2`. Никогда не `Paths64` вручную.
- Erode: `Clipper.InflatePaths(paths, -delta, JoinType.Miter, EndType.Polygon)`. `result.Count == 0` → VANISH (это норма, не исключение); `Count > 1` → SPLIT.
- D_work с препятствиями: `Clipper.Difference(erodedBoundary, dilatedObstacles, FillRule.EvenOdd)`.
- **Ключевая ловушка:** `InflatePaths` на **открытом** пути (EndType.Butt/Square/Round) возвращает **один замкнутый «тубус»** вокруг линии, а не две параллельные кривые. Поэтому обратную ветвь улитки через Clipper2 из open polyline не получить — отсюда Variant C (§5.4).
- Не дублировать первую точку в конце пути (Clipper замыкает сам; дубликат → degenerate edge).
- `PointD.x/.y` строчные, `Point64.X/.Y` заглавные.
- Полигон с holes: просто `PathsD { outer, hole1, hole2 }` + `FillRule.EvenOdd`.

### 4.3. Проверенные «золотые» числа (для регрессионных тестов)

- `square_5x5`, d₀=200, c_wall=50, D_tube=20 → колец **11–13**, длина спирали **115–135 м**.
- `rect_3x6`, d₀=200 → колец **6–8**, длина **75–90 м**.
- DoubleLoop на square_5x5: полная длина **~230 м**, `ratio(DoubleLoop/Spiral) ∈ [1.55, 1.99]`. **Reverse(supply) даёт ровно 2.0 — это детектор заглушки.**
- Каждый сегмент петли ≤ `2·d₀` (длинный сегмент = сломанный Step).
- Каждый сегмент целиком внутри D_work (проверка 11 точками, не midpoint!).

## 5. Проблема обратной ветви — главный технический урок проекта

### 5.1. Симптом

DoubleLoop визуально строится, но на **каждом угловом срезе** (diagonal cut, который делает угловая компенсация) расстояние между подачей и обраткой падает до **40–80 мм** вместо нормы 100 мм. На `square_5x5` константно **44.10 мм** (4 знака точности — не шум, а система). Именно это мы наблюдали как «обратную ветлю корректно сделать не удалось». 5 падающих тестов `Test_DoubleLoop_ParallelSpacing` в ветке — ровно это.

### 5.2. Root cause: concave-side miter shortening

Любой mitered parallel offset (наш `JoinShiftedSegmentsMitered`, Revit `CurveLoop.CreateViaOffset`, Clipper2 `JoinType.Miter`) на **вогнутом изгибе** (поворот в сторону offset'а) геометрически укорачивает внутреннюю кривую на:

```
shortening_per_joint = offset · cot(joint_half_angle)
```

Угловой срез при угле комнаты 90° создаёт стык 135°:

```
shortening = 100 · cot(67.5°) = 100 · 0.4142 = 41.42 мм
```

Внутренняя кривая поворачивает на 41.4 мм **раньше** подачи → диагональный срез внутреннего кольца N проходит в ~44 мм от диагонального среза подачи кольца N+1 → hot-spot.

### 5.3. Это НЕ баг — это свойство геометрии

Python-оригинал через `CurveLoop.CreateViaOffset` даёт **тот же** hot-spot — просто у него нет теста и в Revit это визуально незаметно на мелких срезах. В литературе по offset'ам это классическая проблема reflex-вершин; академическое решение — **straight skeleton** (Palfrader & Held, библиотека SURFER) либо bevel/linear-axis offset вместо miter.

### 5.4. Три пути решения (по возрастанию правильности)

1. **Variant C (реализован в ветке, работает с оговоркой):** обратка = ручной перпендикулярный сдвиг каждого сегмента подачи на d₀/2 + miter/bevel join + **trim самопересекающегося хвоста** у центра + midpoint-мост (как у Python). СНиП-нормы на прямых участках выполняются; hot-spot на срезах остаётся (relaxed-критерий: там только `≤ 350 мм`).
2. **v2.1 §3.3 «Nested Rings» (задокументирован, не реализован):** обе ветви строятся от **общей последовательности колец**, каждое кольцо проходит угловую компенсацию **независимо** на собственном eroded D_work. Срезы соседних колец тогда выровнены по координатам углов комнаты → hot-spot устранён by construction. Ветви = сдвиг base-traversal на ±d₀/4. **Это рекомендуемый путь для следующей реализации.**
3. **Straight skeleton / GEOS offset_curve:** сменить движок offset'а (SURFER-подобный или GEOS ≥ 3.11 `offset_curve` — он умеет открытые кривые). Тяжело, но академически строго.

**Запрещённые симптом-фиксы (все отвергнуты, не повторять):** удаление вершин в угловых зонах; pre-shift компенсация подачи; bevel вместо miter на вогнутых стыках (даёт 76-мм «шпильки» — физически непрокладываемо); `offset/sin(θ)` в перпендикулярном сдвиге (это формула угловой компенсации, не параллельного offset'а — ложная гипотеза BEH-04).

### 5.5. Сопутствующие ловушки Variant C

- **Dedup в miter-join обязателен.** После `SplitSegments(2·d₀)` 60–80% стыков подачи коллинеарны → сдвинутые концы совпадают → без dedup получаем zero-length сегменты → ложные self-intersection → trim сжирает 98–99.7% вершин (баг BEH-05). Правило: `if dist(S_i.End, S_{i+1}.Start) ≤ eps → добавить одну точку, иначе две`.
- **Центр улитки нестабилен:** на внутреннем кольце (радиус ~d₀) offset d₀/2 не помещается → inner curve самопересекается → обязателен `TrimSelfIntersectingTail` + midpoint-мост (прямой мост через центр не работает).

## 6. Инженерные нормы тёплого пола (абсолютные константы, НЕ функции от d₀)

| Константа | Значение | Обоснование |
|---|---|---|
| `MIN_PARALLEL_SPACING` | **100 мм** | Шаг < 100 мм → перегрев поверхности (> 30 °C при теплоносителе 40–50 °C), СНиП |
| `MAX_PARALLEL_SPACING` | **350 мм** | В gap > 350 мм влезает ещё пара труб (100+150+100) → холодное пятно |
| `MIN_U_TURN_SPACING` | **150 мм** | Bend radius PEX-16 = 75 мм × 2; обеспечивается монтажником, не алгоритмом |
| `d₀ допустимый` | **[200, 700] мм** | offset = d₀/2 должен попасть в [100, 350] |

Отсюда же: центральная непокрытая зона улитки ≤ 350×350 мм — приемлемо (центр комнаты теплее).

| Serpentine, IslandTraverser (holes) | ❌ Не реализованы | — |

**Вердикт по коду:** сам код можно удалять вместе с веткой — всё ценное из него извлечено в §4–§6 этого документа. Если фича возродится, честный рестарт по этому документу + Clipper2 будет быстрее, чем воскрешение ветки.

## 8. Провальные подходы — НЕ повторять

### 8.1. v8 (scalar field + графы + MILP)

Вертикальные полосы через `ScalarField` — это не спираль и не змейка. Для детерминированной спирали **не нужны**: графы состояний, lane events, MILP/DP/FPTAS solver'ы, Morse-анализ, persistent homology. Нужны: offset, ближайшие точки, прямые перемычки.

### 8.2. Анти-паттерны реализации (F1–F20, сжато)

| # | Анти-паттерн | Детектор |
|---|---|---|
| F1 | Кольца через BoundingBox вместо реального offset | L-shape: bbox-area > area·1.1 |
| F2 | Clipper2-адаптер-пустышка (возвращает вход) | offset квадрата 5000 на −200 → 4600×4600 |
| F4 | Спираль склейкой вершин колец (без Shot/Step) | разрывы/прыжки > d₀ на стыках |
| F5/F11 | DoubleLoop = supply + Reverse(supply) | ratio длин = ровно 2.0 (реальный ∈ [1.55, 1.99]) |
| F9 | Проверка сегмента только по midpoint | диагональный мост через комнату проходит тест! Проверять 11 точек |
| F10 | Сегменты длиннее 2·d₀ | любой такой сегмент = сломанный Step |
| F16 | Самодельный fallback (сдвиг к centroid и т.п.) | на вогнутых формах centroid снаружи → катастрофа |
| F17 | `catch { break/return null/continue; }` | тихий обрыв спирали после 1 кольца, ложно-зелёные тесты |
| F18 | Ослабление assert'ов ради зелёного CI | изменение теста = изменение спецификации, требует одобрения |

| F20 | Мост туда-обратно (bridgeOut = Reverse(bridgeIn)) | это не обход препятствия, а петля на месте |

### 8.3. Мета-уроки процесса

- Цикл **Plan → Contract → Test → Code**. Код до согласованного псевдокода = agent drift.
- PoW-гейт после каждой фазы: тест, который физически невозможно пройти заглушкой.
- Не «чинить спецификацию эвристиками»: если реализация начала «помогать» алгоритму — это drift.
- Сначала классификация (баг кода vs ограничение архитектуры), потом фикс.

## 10. Внешний контекст и ссылки

- **Наша задача = Coverage Path Planning (CPP), класс «spiral pattern».** Академически подтверждённый подход: спиральные паттерны через Morse-декомпозицию (Acar & Choset), Spiral-STC (Gabriely & Rimon 2002), linked spiral paths (Choi et al. 2009). Обзоры: Galceran & Carreras, «A survey on coverage path planning for robotics» (2013); свежий обзор 125 работ — arXiv:2607.10649 (2026). Классическая змейка в CPP = **boustrophedon** (Choset & Pignon 1997).
- **Offset-кривые:** miter-shortening на вогнутых стыках — известная проблема; Palfrader & Held, «Computing Mitered Offset Curves Based on Straight Skeletons» (CADA 2015) + библиотека SURFER. GEOS ≥ 3.11 `offset_curve` (см. shapely) — reference-реализация offset'а открытых кривых.
- **Clipper2:** https://github.com/AngusJohnson/Clipper2 (C# в `CSharp/Clipper2Lib`). NuGet `Clipper2`.
- **Альтернативная философия:** `felixscode/opti-pipe` — Python-библиотека укладки тёплого пола через grid-граф + DFS-эвристику + симуляцию теплораспределения. Работает только на прямоугольных комнатах; полезна как референс «другого пути» и как источник идеи тепловой визуализации.
- **Revit-механика (для будущего плагина):** вход — `FilledRegion.GetBoundaries()`; трубы — `Pipe.Create` + `RBS_PIPE_DIAMETER_PARAM`; отводы — `doc.Create.NewElbowFitting(ClosestConnectors(...))`; единицы — футы (`/304.8`).

## 11. Продуктовое направление (принятые решения)

1. **Зоны задаёт проектировщик вручную** (области маскировки / FilledRegion), как в оригинальном скрипте. Автоматическое деление помещения на зоны контурирования — признано нерешаемым «в лоб» и **отменяется**. Это снимает самую тяжёлую часть (§14 holes, multi-island ordering, split ownership) на уровне продукта.
2. **Паттерны:** главный — **улитка** (DoubleLoop). Одиночная спираль — диагностика. Классическая змейка — позже, по отдельному дизайну (в CPP-литературе = boustrophedon; дизайн: проходы вдоль длинной стороны, U-turn 180° на границах, подача→обратка через последний разворот). §12 v2.0 (ring-based U-turn) — не реализовывать.
3. **Расчётный модуль (тепло/гидравлика) — вне геометрического ядра.** Архитектура из методички §21: `Physics Adapter → CoreParams (d₀, Lmax…) → GOTK.Core (чистая геометрия) → Physics Adapter (проверка ΔP/q/v → warm-start с новым d₀)`. Ядро ничего не знает про тепло; расчётчик задаёт d₀ зонально.
4. **Дорожная карта ядра при возрождении:** Spiral (решено, §4) → DoubleLoop по v2.1 §3.3 nested-rings (§5.4, путь 2) → AttachSupply к трубам + Chamfer (формулы §2.5, §2.7) → Revit-адаптер (Pipe/Elbow, §10) → Lmax-разбиение петель → расчётный модуль d₀.
