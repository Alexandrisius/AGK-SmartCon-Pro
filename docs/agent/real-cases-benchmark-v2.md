## Как работать с этим файлом (инструкция для агента новой сессии)

1. **Владелец надиктовывает кейс голосом** (возможны неточности распознавания).
   Твоя обязанность — уточнить всё до идеального понимания: что дано, что должно
   получиться, какой масштаб. Вопросы задавай коротко и по существу.
2. **Оформи кейс по шаблону ниже** и пометь статус. Уточнения владельца вписывай
   в поля кейса (дословные ответы — в «Заметки»).
3. **Санитарная проверка кейса перед включением** (все три — да, иначе кейс не
   принимается):
   - **Решаемость:** решается существующими тулами каталога ИЛИ тулом, который
     реально добавить за ночь. API-невозможное — не кейс (см. «Отклонённые»).
   - **Текст без имён тулов:** в промпте для LLM — только задача как от
     проектировщика. Никаких «используй start_job».
   - **Проверяемость:** критерий «что должно получиться» проверяется состоянием
     модели (коллекторы/значения/имена), а не самочувствием модели.
4. **Отклонённый кейс — не удалять:** переносить в раздел «Отклонённые» с
   причиной. Это защита от повторного предложения того же.
5. Перед ночным прогоном: каждый кейс в статусе `ready` получает сид+вердикт в
   харнессе `src/SmartCon.IntegrationTests/Agent/AgentRealCasesBenchmarkTests.*`
   (образцы — Case3/Case4/Case5; MaxRoundsPerTask=20, LLM-таймаут 240с/вызов уже
   стоят; промпты дословно из этого файла + стартовый блок из archive-файла).

### Шаблон кейса

```markdown
## Кейс N: <короткое имя>  [ready | draft | blocked-уточнение | done]
- **Текст задачи для LLM (дословно, без имён тулов):** «…»
- **Что должно получиться (проверяемо):** …
- **Сид:** … (уровни/виды/семейства/ФОП/… — что создать в тестовой модели)
- **Эталоны/конвенции:** … (имена-образцы, паттерны, префиксы — всё, что
  в реальности у каждого проекта своё и должно даваться кейсом, не хардкодом)
- **Ожидаемые инструменты:** … (какие есть; каких не хватает — задача ночи)
- **Заметки (ответы владельца дословно):** …
```

## Кейс 1: Массовое создание планов этажей по системам  [ready]

- **Текст задачи для LLM (дословно, без имён тулов):**
  «Уровни уже скопированы в модель из координационной связи. Создай планы этажей
  для моих систем: на каждом уровне — по плану каждой системы, с шаблоном вида
  этой системы. Шаблон должен быть применён по-настоящему — чтобы настройки
  планов управлялись из шаблона централизованно. Имена — по образцу
  существующего дефолтного вида "В_Этаж 1_Отопление": префикс и система как в
  образце, меняется только этаж (по уровню, на котором создан план).»
- **Что должно получиться (проверяемо):**
  - N уровней × M систем планов этажей создано;
  - каждый план имеет **назначенный ViewTemplateId** шаблона своей системы
    (не только скопированные настройки — централизованное управление);
  - имена точно по паттерну эталона, номер этажа соответствует уровню вида
    (у вида есть read-only свойство «уровень создания» — источник истины для
    этажа; от него же считается секущий диапазон);
  - дефолтные виды-эталоны не тронуты; никаких дубликатов имён.
- **Сид (компактный — «кейс оч прост, не затягивать работу LLM»):**
  5 уровней; 2 шаблона видов систем (например «Отопление», «Канализация»);
  1 дефолтный вид-эталон на последнем уровне с именем «В_Этаж 1_Отопление».
- **Эталоны/конвенции:** эталон имени **у каждого проекта свой** (владелец:
  «в каждой модели может быть разный, мы делаем универсальный харнесс») —
  кейс всегда даёт образец в сиде; тулы не хардкодят паттерн.
- **Ожидаемые инструменты:** `create_floor_plans` — **НЕТ, создать ночью**
  (levels[] + templateId + applyTemplate:назначить ViewTemplateId +
  namePattern с подстановкой этажа из уровня вида; пачка уровней одним
  вызовом). Проверка — существующие read-туры (`list_views`, get_view_settings).
  Альтернатива существующими: create_view поштучно + apply_view_template +
  rename_views — но 5×2 вызовов; идеал — один-два вызова на пачку.
- **Заметки (ответы владельца дословно):**
  - эталон в его шаблоне: «В_Этаж 1_Отопление»;
  - «да вообще пофиг [состав пачек/уровней]. кейс оч просто и не нужно
    затягивать работу LLM» → компактный сид;
  - «да, получить шаблон вида» (намертво);
  - разрезы: «не включаем. пусть будут только планы этажей»;
  - механика «галочки»: при создании вида с шаблоном настройки КОПИРУЮТСЯ, но
    View Template остаётся None — отсюда двойной ручной шаг владельца
    (создать → выделить все → применить шаблон). Тул обязан делать оба шага.

## Отклонённые кейсы (не тестировать; причина зафиксирована)

### Кейс 0a: Скрыть оси/уровни связанных моделей (workset «Общие уровни и сетки» в Display Settings связи)  [отклонён 2026-11-22]

- **Причина:** API не может ни читать, ни писать вкладки «Рабочие наборы» и
  «Категории» настроек отображения связи (проверено 2026-11-22: класс
  RevitLinkGraphicsSettings в API 2025–2027 покрывает только вкладку «Основные»;
  Jeremy Tammik/ADN 15326569; Boost Your BIM AU2024: «as far as we can go»).
  Агент слеп к предпосылке и результату → угадывание; обходные пути
  (перезагрузка связи с WorksetConfiguration, ByLinkView, перенос готового
  шаблона) — решено НЕ гонять кейсом: владелец — «если у агента не будет тулов,
  он будет 3 часа искать».
- **Ручной метод владельца (best practice, подтвердил Autodesk help):**
  V/G → Revit Links → Display Settings → Custom → Worksets → выкл
  «Общие уровни и сетки» у каждой связи; делается в шаблоне вида.
- **Отложенные дешёвые задачи (по желанию, не кейсы):** read-туры по связям
  (список связей + их рабочие наборы через связанный документ + Basics-настройки);
  тул «перезагрузить связь с закрытыми наборами» (dry-run).
