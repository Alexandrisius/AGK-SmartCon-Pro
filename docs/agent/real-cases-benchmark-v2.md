# Real-cases benchmark v2 — живой SSOT кейсов ночного прогона

> **Назначение файла:** здесь живут реальные кейсы владельца (надиктованные) для
> живых прогонов ИИ-агента SmartCon. Файл — единственный источник правды по кейсам
> текущей волны. Предыдущая волна (5 кейсов, закрыта 2026-11-21) — в
> `archive/00-strategy/real-cases-benchmark.md` и issue #445.
>
> **Статус:** наполняется. Кейсов в цели: 10. Готово: 5 (+1 отклонён с обоснованием).

---

## Как работать с этим файлом (инструкция для агента новой сессии)

1. **Владелец надиктовывает кейс голосом** (возможны неточности распознавания).
   Твоя обязанность — уточнить всё до идеального понимания: что дано, что должно
   получиться, какой масштаб. Вопросы задавай коротко и по существу.
2. **Оформи кейс по шаблону ниже** и пометь статус. Уточнения владельца вписывай
   в поля кейса (дословные ответы — в «Заметки»).
3. **Санитарная проверка кейса перед включением** (все три — да, иначе кейс не
   принимается):
   - **Решаемость:** решается существующими тулами каталога ИЛИ тулом, который
     реально добавить за ночь. API-невозможное — не кейс (см. «Отклонённые»).
   - **Текст без имён тулов:** в промпте для LLM — только задача как от
     проектировщика. Никаких «используй start_job».
   - **Проверяемость:** критерий «что должно получиться» проверяется состоянием
     модели (коллекторы/значения/имена), а не самочувствием модели.
4. **Отклонённый кейс — не удалять:** переносить в раздел «Отклонённые» с
   причиной. Это защита от повторного предложения того же.
5. Перед ночным прогоном: каждый кейс в статусе `ready` получает сид+вердикт в
   харнессе `src/SmartCon.IntegrationTests/Agent/AgentRealCasesBenchmarkTests.*`
   (образцы — Case3/Case4/Case5; MaxRoundsPerTask=20, LLM-таймаут 240с/вызов уже
   стоят; промпты дословно из этого файла + стартовый блок из archive-файла).

### Шаблон кейса

```markdown
## Кейс N: <короткое имя>  [ready | draft | blocked-уточнение | done]
- **Текст задачи для LLM (дословно, без имён тулов):** «…»
- **Что должно получиться (проверяемо):** …
- **Сид:** … (уровни/виды/семейства/ФОП/… — что создать в тестовой модели)
- **Эталоны/конвенции:** … (имена-образцы, паттерны, префиксы — всё, что
  в реальности у каждого проекта своё и должно даваться кейсом, не хардкодом)
- **Ожидаемые инструменты:** … (какие есть; каких не хватает — задача ночи)
- **Заметки (ответы владельца дословно):** …
```

## Кейс 1: Массовое создание планов этажей по системам  [ready]

- **Текст задачи для LLM (дословно, без имён тулов):**
  «Уровни уже скопированы в модель из координационной связи. Создай планы этажей
  для моих систем: на каждом уровне — по плану каждой системы, с шаблоном вида
  этой системы. Шаблон должен быть применён по-настоящему — чтобы настройки
  планов управлялись из шаблона централизованно. Имена — по образцу
  существующего дефолтного вида "В_Этаж 1_Отопление": префикс и система как в
  образце, меняется только этаж (по уровню, на котором создан план).»
- **Что должно получиться (проверяемо):**
  - N уровней × M систем планов этажей создано;
  - каждый план имеет **назначенный ViewTemplateId** шаблона своей системы
    (не только скопированные настройки — централизованное управление);
  - имена точно по паттерну эталона, номер этажа соответствует уровню вида
    (у вида есть read-only свойство «уровень создания» — источник истины для
    этажа; от него же считается секущий диапазон);
  - дефолтные виды-эталоны не тронуты; никаких дубликатов имён.
- **Сид (компактный — «кейс оч прост, не затягивать работу LLM»):**
  5 уровней; 2 шаблона видов систем (например «Отопление», «Канализация»);
  1 дефолтный вид-эталон на последнем уровне с именем «В_Этаж 1_Отопление».
- **Эталоны/конвенции:** эталон имени **у каждого проекта свой** (владелец:
  «в каждой модели может быть разный, мы делаем универсальный харнесс») —
  кейс всегда даёт образец в сиде; тулы не хардкодят паттерн.
- **Ожидаемые инструменты:** `create_floor_plans` — **НЕТ, создать ночью**
  (levels[] + templateId + applyTemplate:назначить ViewTemplateId +
  namePattern с подстановкой этажа из уровня вида; пачка уровней одним
  вызовом). Проверка — существующие read-туры (`list_views`, get_view_settings).
  Альтернатива существующими: create_view поштучно + apply_view_template +
  rename_views — но 5×2 вызовов; идеал — один-два вызова на пачку.
- **Заметки (ответы владельца дословно):**
  - эталон в его шаблоне: «В_Этаж 1_Отопление»;
  - «да вообще пофиг [состав пачек/уровней]. кейс оч просто и не нужно
    затягивать работу LLM» → компактный сид;
  - «да, получить шаблон вида» (намертво);
  - разрезы: «не включаем. пусть будут только планы этажей»;
  - механика «галочки»: при создании вида с шаблоном настройки КОПИРУЮТСЯ, но
    View Template остаётся None — отсюда двойной ручной шаг владельца
    (создать → выделить все → применить шаблон). Тул обязан делать оба шага.

## Кейс 2: Приведение общих параметров семейств к ФОПу заказчика  [ready]

- **Текст задачи для LLM (дословно, без имён тулов):**
  «Заказчик прислал свой файл общих параметров — вся отчётность по модели должна
  собираться на его параметрах. Сейчас размещённые в модели семейства попадают
  в ведомости с пустыми строчками: их общие параметры родом из старых, чужих
  файлов параметров. Приведи размещённые семейства к параметрам заказчика так,
  чтобы отчётность, которая идёт заказчику, собиралась заполненной: проанализируй,
  какие общие параметры у семейств сейчас и из каких они наборов, замени их на
  аналоги из нового файла, перенеся все заполненные значения — наименование,
  марка, единицы измерения, завод-изготовитель и т.п. Работай пакетно и аккуратно:
  семейств много, они собраны из разных источников, вручную это недели. Если у
  семейства нужного параметра нет или значение пустое — ничего не придумывай,
  собери мне отдельный список, что доделать руками, и подготовь способ быстро
  увидеть остаток проблемных семейств. Семейства, не размещённые в модели, пока
  не трогай — покажи их отдельным списком.»
- **Что должно получиться (проверяемо):**
  - все размещённые семейства (10 из сида) имеют общие параметры с GUID
    определений ФОПа заказчика; значения перенесены из старых аналогов;
  - целевой набор = поля сид-ведомости «Ведомость объёмов работ», размещённой
    **на листе**; черновая ведомость вне листов НЕ повлияла на набор (её поля
    не мигрируются) — проверка суждения «критичное = вынесено на лист»;
  - 2 семейства-инвалида честно подсвечены в отчёте «доделать руками» с
    причиной (значение-источник пустое / параметра-источника нет вообще),
    значения не выдуманы;
  - 2 неразмещённых семейства не тронуты (исходные параметры на месте) и
    перечислены отдельным блоком «можно продолжить по команде»;
  - существует контрольная ведомость с фильтром по пустому значению целевого
    параметра и идентифицирующими полями (семейство/тип/размер) — способ
    увидеть остаток проблемных;
  - миграция пакетная (пачки по группам), не поштучная — грейдер следит как
    в кейсе 2 прошлой волны.
- **Сид (12 семейств / 4 исходных ФОП-группы; сложность в разнообразии, не
  в количестве):**
  - целевые определения (уже в проекте, «ФОП заказчика подключён»): 5 шт. —
    Наименование, Марка, Единица измерения, Завод-изготовитель, Артикул;
  - группа А (5 семейств: 4 с экземплярами, 1 без): параметры {А_*}, все
    значения заполнены;
  - группа Б (4 семейства: 3 с экземплярами, 1 без): параметры {Б_*}, набор
    неполный (нет аналога «Завода») — переносится то, что есть;
  - группа В (2 семейства, оба с экземплярами): параметры {В_*}, у одного
    «наименование» пустое → инвалид «значение пустое»;
  - группа Г (1 семейство, с экземпляром): источников почти нет (только
    марка) → инвалид «параметра нет вообще»;
  - сид-ведомость «Ведомость объёмов работ» с полями из целевых параметров,
    размещённая на листе; на листе пара видов (сигнал «модель в полировке»);
  - приманка: черновая ведомость НЕ на листе, поля из старых параметров
    группы А — на неё вестись нельзя.
- **Эталоны/конвенции:** имена параметров и групп у каждого проекта свои —
  сид даёт условные; суть группировки — разные наборы GUID исходных общих
  параметров. Целевой набор всегда определяется моделью (поля критичной
  ведомости), не хардкодом тулов.
- **Ожидаемые инструменты:** миграционная механика готова и доказана живым
  dogfood (map_family_parameters с createTarget, batch + preview/undo;
  replace_family_parameter two-step). Не хватает (задача ночи):
  1) read-тур «группировка семейств по сигнатуре исходных общих параметров» —
     по наборам GUID («50 семейств с одним ФОПом, 20 с другим, 100 с третьим»);
  2) чтение полей конкретной ведомости + признак «размещена на листе»
     (ScheduleSheetInstance) — источник целевого набора;
  3) создание контрольной ведомости с фильтром пустых значений и полями
     семейство/тип/размер (тул создания ведомостей, если его ещё нет).
- **Заметки (ответы владельца дословно):**
  - максимальная автономия: «все хотят чтобы агент лучше лишнюю минуту сам
    проанализировал существующие спецификации и сам понял»; пользователь может
    назвать атрибуты сам, но по умолчанию агент не останавливается и не спрашивает;
  - критичность: «агент должен сам догадаться что есть спецификация вынесенная
    на лист который называется ведомость объемов работ и что все поля в данной
    спецификации это критически важные атрибуты»; «есть временные расчётные…
    на коленке сделанные… а есть для оформления которые вынесены на листы»;
  - маппинг: агент сопоставляет старые параметры с новыми сам (имена почти
    никогда не совпадают один-в-один), план показывает перед применением;
  - экземпляры: «если модель уже большая… идёт какая-то полировка — можно
    ставить перед фактом: я переделал семейства которые выставлены в модели,
    чтобы текущее состояние модели можно было уже передать заказчику…
    минимальной кровью; если пользователь просит дальше — агент будет менять
    дальше»; «нужно чтобы наш агент не тупо отчёт выполнял, а именно логически
    думал»;
  - масштаб: «задача не в количестве семейств, это рутинная монотонная работа,
    а именно в разнообразии и сложности» — 12 семейств / 4 группы согласовано;
  - ФОП-файл: «фоп это текстовый файл txt и там может быть 100-200 параметров
    в разных группах» — умный поиск по файлу ФОПа отдельная мысль (в этом кейсе
    параметры заказчика уже в проекте; поиск по файлу — кандидат в тулы позже).

## Кейс 3: Перевод спецификаций на ФОП заказчика (замена на месте, старые — в архив)  [ready]

- **Текст задачи для LLM (дословно, без имён тулов):**
  «Заказчик прислал свой файл общих параметров — вся отчётность должна собираться
  на его параметрах. Отчётность в модели уже настроена и оформлена по ГОСТу:
  ведомости вынесены на листы, у каждой настроены колонки с ширинами и
  заголовками, скрытые столбцы, сортировки, фильтры, группировки с итогами,
  стиль таблиц, своё положение на листе. Переведи всю отчётность, которая идёт
  заказчику, на параметры из его файла: для каждой такой ведомости собери точный
  аналог на новых параметрах, перенеся оформление и настройки один-в-один —
  порядок и заголовки колонок, ширины, скрытые столбцы, сортировку, фильтры,
  группировки и итоги, стиль таблиц. Новая ведомость должна получить имя старой
  и встать на листе ровно на её место. Саму старую не удаляй и не оставляй на
  листе — переименуй её как архивную (с пометкой «Архив» в имени), чтобы я мог
  подсматривать, как она была настроена, если в новой что-то упустим. Если у
  какого-то поля не находится аналога в новом файле параметров — колонку пропусти
  и покажи мне список таких мест.»
- **Что должно получиться (проверяемо):**
  - для каждой вынесенной на лист ведомости сида: существует новая с **тем же
    именем**, поля — аналоги из ФОПа заказчика; порядок колонок, заголовки,
    ширины, скрытость, сортировка, фильтры, группировки/итоги, стиль таблиц —
    совпадают с оригиналом (для колонок, у которых есть аналог);
  - новая размещена на листе **на месте старой** (тот же лист, та же позиция
    в пределах допуска, заголовок выноса);
  - старая спека жива в проекте (для подсматривания), имя содержит «Архив»,
    с листа снята;
  - колонки без аналога в ФОПе заказчика пропущены и перечислены в отчёте;
  - черновая ведомость вне листов не тронута (имя/поля) — проверка того же
    суждения «критичное = на листе»;
  - строки новой ведомости заполнены данными (сид даёт элементам оба набора
    параметров — как будто миграция семейств из кейса 2 уже прошла).
- **Сид (3 спеки + приманка; разные категории):**
  - целевые определения ФОПа заказчика уже в проекте (как в кейсе 2): 5–6 шт.;
  - элементы (например, оборудование и арматура) с заполненными СТАРЫМИ
    параметрами (АДСК-набор) и заполненными НОВЫМИ (заказчик) — правдоподобие
    «семейства уже переведены»;
  - «большая» ведомость по ГОСТу: 8–10 колонок, скрытые столбцы, свои ширины,
    сортировка 2 уровня, фильтр, группировка с итогами — на листе;
  - средняя (5–6 колонок) и простая (3 колонки) — на листе (одна из них на
    листе с несколькими ведомостями);
  - приманка: черновая ведомость НЕ на листе со старыми полями — не трогать.
- **Эталоны/конвенции:** пометка архива — суффикс или префикс «Архив» (даётся
  кейсом; у проекта может быть своя конвенция). Имена спек переносятся от
  оригиналов, не изобретаются.
- **Ожидаемые инструменты:** НЕ хватает (задача ночи):
  1) read-детализация ведомости: поля + порядок + ColumnHeading + ColumnWidth +
     IsHidden + сортировки + фильтры + итоги/группировка + стиль таблиц +
     вынос (лист/позиция/заголовок) — база: ScheduleDefinition/TableStyle/
     ScheduleSheetInstance; API-границы (сегменты заголовков, поворот выноса)
     доказать Exa'ой до кода;
  2) write-тул «пересобрать ведомость на новых полях»: создать с тем же именем,
     перенести все переносимые настройки, поля заменить по маппингу
     старый→новый (маппинг агент строит сам, как в кейсе 2);
  3) операции выноса: снять старую с листа, разместить новую на её месте
     (SheetInstance create/remove).
- **Заметки (ответы владельца дословно):**
  - замена на месте: «если спецификация уже вынесена на лист, то вынос её
    удаляем и ставим свою — нам не нужны две спецификации с итоговыми данными;
    старая может стать пустой, если мы заменили параметры на новые;
    следовательно саму спецификацию оставляем, чтобы не удалять её, но вынос
    её убираем и на это место размещаем нашу новую»;
  - имена: «называть нужно точно так же, как старая спецификация; только
    старым спецификациям нужно сначала поставить какой-то флаг, что они
    архивные — суффикс или префикс "архив"… чтобы они в одну папочку
    хлопнулись архивные… чтобы мы могли подсматривать, как они были настроены,
    если мы что-то упустим у себя»;
  - про «папочку» в диспетчере проекта: группировка параметром/браузерной
    организацией — в реальном шаблоне владельца организация настраивается в
    UI диспетчера (создание BrowserOrganization через API недоступно — как в
    кейсе 1 прошлой волны); в кейсе критерий — имя с «Архив»; если у модели
    уже настроена организация по изменяемому параметру, агент может выставить
    и его — бонусом, не блокером;
  - масштаб: 3 спеки + приманка — согласовано; «максимум что API позволяет
    узнать про форматирование — то и узнаём».

## Кейс 4: 3D-вид на каждую систему (фильтр по общему параметру имени системы)  [ready]

- **Текст задачи для LLM (дословно, без имён тулов):**
  «В модели смоделированы трубопроводные системы. Мне нужно по 3D-виду на каждую
  систему: вид показывает только элементы одной системы и называется её именем.
  Сложность в том, что системное свойство «Имя системы» не достаётся вложенным
  семействам — в проекте для этого заведён общий параметр «АДСК_ИмяСистемы»,
  который должен повторять имя системы у всех элементов, включая вложенные
  общие семейства (фланцы и т.п.), иначе фильтр вида их не покажет. Сейчас он
  заполнен не везде. Оформи каждый вид на базе нашего шаблона 3D-вида и фильтром
  по этому общему параметру. Сначала разберись, какие имена систем есть в модели
  и все ли названы руками: если увидишь похожие автодубликаты вроде «Т11» и
  «Т111» — не делай на них виды, покажи мне их отдельно как подозрение на разрыв
  системы, а список имён, по которым сделаю виды, утверди у меня.»
- **Что должно получиться (проверяемо; кейс двухшаговый — интерактив):**
  - шаг 1 (анализ): агент собрал уникальные имена систем, разделил на чистые
    (вручную: «Т1», «Т1.11» с точкой) и подозрительные (автосуффиксы без
    точки, префикс-группы), показал список к утверждению; подозрительные —
    отдельно с пометкой «похоже на разрыв системы»; харнесс отвечает
    согласием → шаг 2;
  - шаг 2 (работа): для каждой чистой системы создан 3D-вид: имя = имени
    системы; назначен общий шаблон 3D-вида (один на все виды); на вид добавлен
    фильтр «АДСК_ИмяСистемы = имя системы»;
  - общий параметр «АДСК_ИмяСистемы» заполнен именем системы у ВСЕХ элементов
    каждой чистой системы: трубы, фитинги, оборудование **и вложенные общие
    семейства (субкомпоненты-фланцы)** — сердце кейса;
  - на подозрительные имена видов НЕТ; они подсвечены в итоговом отчёте;
  - шаблон один; фильтры живут на видах (в шаблоне секция фильтров не
    управляется шаблоном — сид это гарантирует, агент не должен включать).
- **Сид (5 имён систем, трубы + фитинги + оборудование с фланцами):**
  - 3 чистые системы: «Т1», «Т2», «Т1.11» (точка = ручное именование);
  - подозрительная группа: «Т11» и «Т111» (автосуффикс Revit; физически —
    вероятно один разорванный контур);
  - трубы + фитинги каждой системы; 2 единицы оборудования (насосы), у каждого
    вложенное общее семейство-фланец (shared nested), у фланцев общий параметр
    пуст — наследование не сделано;
  - общий параметр-приёмник «АДСК_ИмяСистемы» (конвенция проекта, даётся
    кейсом) заполнен частично (например, у труб есть, у фитингов нет);
  - шаблон 3D-вида: один, с НЕуправляемой шаблоном секцией фильтров
    (Include-галочка «Фильтры» снята — как в реальном шаблоне владельца).
- **Эталоны/конвенции:** имя общего параметра-двойника у каждого проекта своё
  (здесь «АДСК_ИмяСистемы») — даётся кейсом; чистое имя = без «кучи цифр»,
  многоуровневые суффиксы через точку.
- **Ожидаемые инструменты:** существующие: create_view (3d), фильтры видов
  (создание/применение), set_view_template_inclusion (Include-галочка — уже
  доказана). Не хватает (задача ночи):
  1) read-тур «имена систем»: уникальные значения системного «Имя системы» по
     MEP-категориям + классификация чистые/подозрительные (префикс-группы,
     суффиксы без точки);
  2) write-джоба «заполнить общий параметр именем системы»: для каждой системы
     проставить общий параметр всем элементам И субкомпонентам (shared nested)
     от родителя;
  3) пакетное создание 3D-видов с фильтром (по духу create_floor_plans кейса 1:
     пачка, не поштучно);
  4) опционально (nice-to-have): подсветка «места разрыва» — элементы двух
     имён систем, физически соседние/соединённые (владелец: «пока не умеем
     исправлять — можем подсветить»).
- **Заметки (ответы владельца дословно):**
  - на подозрительные виды не создавать: «создавать отдельные виды конечно же
    не хотелось бы, потому что проектировщик их всё равно удалит; но спрашивать
    тоже не показатель классного каркаса — вы должны сами разобраться»; «в
    модели может быть тысяча похожих имён — не должен создавать тысячу тупых
    видов… можно показать: вот список имён систем, по которым будут созданы
    виды — утверждаете / не утверждаете» (вопрос здесь нормален);
  - как думает проектировщик: «я бы решал проверкой того, что является стыком
    этих разных имён систем — возможно, там какое-то семейство неправильное,
    которое нужно подсветить; бывает что просто забыли соединить трубу —
    тогда забыли назвать или забыли соединить»;
  - шаблон: «никто не создаёт шаблон под каждый вид — сотни шаблонов это
    плохая практика; делается один красивый шаблон вида, и в нём должна быть
    убрана галочка фильтра, чтобы на одном шаблоне вида использовать разные
    фильтры — создаём 100 видов трубопроводов с одним шаблоном, но с разными
    фильтрами»;
  - системный атрибут: «имя системы не наследуется вложенными семействами
    (фланец, который должен быть подсчитан спецификацией) — почти всегда есть
    отдельный общий параметр, в который переписывают имя системы, включая
    вложенные общие семейства от родителя, чтобы фильтр отобразил всё»;
  - детект: префикс-группы + суффиксы — согласовано (Recommended принят);
  - масштаб: 5 систем + фланцы — согласовано.

## Кейс 5: Заполнение «Код по классификатору» по атрибутам семейств  [ready]

- **Текст задачи для LLM (дословно, без имён тулов):**
  «К модели подключён классификатор — иерархический текстовый файл рядом с
  моделью (razdel › подраздел › элемент, коды вида "30.20.10"). Заполни
  параметр "Код по классификатору" на уровне типоразмера у всех семейств
  модели: проанализируй каждое семейство — категорию, имя, значения общих и
  системных параметров, имя типоразмера — и подбери самый подходящий код из
  классификатора. Обычно всем типоразмерам одного семейства подходит один код,
  но если типы реально различаются по классификации (например труба стальная,
  медная и пластиковая — это разные типоразмеры) — у каждого типа свой код.
  В итоге покажи: каким семействам какие коды присвоены и каким путём по
  классификатору (раздел › подраздел › элемент), и отдельно — что не удалось
  уверенно классифицировать.»
- **Что должно получиться (проверяемо):**
  - у всех 8 семейств сида параметр «Код по классификатору» заполнен
    ОЖИДАЕМЫМ кодом (истина известна сиду заранее);
  - два режима в одном сиде: (а) семейства с несколькими типоразмерами
    (кран Ду15/Ду25) — одинаковый код, но ЗАПИСАННЫЙ В КАЖДЫЙ типоразмер
    (Revit принимает код на типоразмер: проверка — у обоих типов крана
    параметр заполнен, а не только у первого); (б) системная труба с типами
    «Сталь», «Медь», «ПВХ» — три РАЗНЫХ кода;
  - в ответе агента для каждого решения — путь по классификатору
    (хлебные крошки), а не голый код;
  - неуверенные случаи честно перечислены, коды не выдуманы мимо
    классификатора;
  - бонус-метрика (не блокер): экономия контекста — воспользовался ли агент
    семантическим выбором из большого списка вместо чтения всех ~120 строк
    в свой контекст (число строк, попавших в контекст агента).
- **Сид:**
  - классификатор ~120 строк, 3 уровня, коды «XX.YY.ZZ», русские названия,
    две ветки: АР (проёмные/стены/свет) и MEP (трубопроводная арматура/
    оборудование); файл-текст рядом с моделью;
  - 8 семейств: кран шаровой (2 типа), задвижка, насос, фильтр сетчатый +
    дверь, окно, колонна, светильник; коды пустые;
  - у части семейств богатые общие параметры (Назначение, Материал), у
    1–2 бедные (решать по имени семейства);
  - системное семейство трубы с 3 типоразмерами: «Сталь», «Медь», «ПВХ» —
    в классификаторе для них есть отдельные коды (материальная ветка).
- **Эталоны/конвенции:** формат кода и файл классификатора у каждого проекта
  свои — даются кейсом. Имена параметра — системное «Код по классификатору»
  (Assembly Code).
- **Ожидаемые инструменты:** НЕ хватает (задача ночи):
  1) **`semantic_match` — тул семантического выбора (ОБЯЗАТЕЛЕН, решено
     владельцем):** вход — массив строк (с уже сшитыми хлебными крошками
     «раздел › подраздел › элемент») + запрос-описание; внутри — вызов малой
     модели (decision-инфраструктура, наш ключ); выход — топ-K кандидатов со
     скорами, НЕ весь список. Переиспользуемый блок: этот же тул обслужит
     кейс 2 («какой параметр ФОПа заказчика больше всего похож на наш») и
     будущее «точечного семантического поиска по большим массивам»;
  2) read-тур классификатора: парсинг иерархического txt в строки с крошками;
     источник файла — путь из задачи (ночью проверить API: читается ли путь
     подключённого классификатора из модели);
  3) batch-запись AssemblyCode типоразмерам (проверить существующие write-пути
     параметров типов; API-факт на ночь: AssemblyCode — строковый параметр
     типоразмера, пишется свободно, файл классификатора нужен только UI-пикеру).
- **Заметки (ответы владельца дословно):**
  - «код по классификатору — системный параметр, заполняется в типоразмере;
    классификатор может быть большой, 100–200 строчек — классно иметь
    помощника — модель принятия решений, которая подсказывает, какой код
    выбрать»;
  - «почти всегда иерархическое дерево — нужно собрать строки с хлебными
    крошками, чтобы обогатить контекст листьев, и отдать список модели
    принятия решений; если ты всё это прочитаешь сам — теряется смысл
    экономии контекста»;
  - «мы не можем себе придумать тул-скрипт на лету — нужен отдельный тул,
    который сшивает категории в одну строчку и отправляет в модель»;
  - «задача лёгкая, возможно модель принятия решений не обязательна — но
    помогла бы экономить контекст» → главный критерий — верные коды,
    экономия — бонус-метрика;
  - «сюда же ложится ФОП заказчика: весь столбец наименований (200 строк)
    отправить модели — какая больше всего похожа на наш параметр»;
  - «агент быстро забивает контекст: семейства с сотнями атрибутов,
    спецификации, куча данных — научить точечно получать данные по
    семантическому поиску; модель принятия решений — это и есть
    семантический поиск, не требующий сложного конвейера» → ночью оформить
    issue-направление «точечный семантический поиск по большим массивам»;
  - типоразмеры: «редко у типоразмеров разный код, но если классификатор
    супер-подробный — трубопроводы сделаны типоразмерами: стальная, медная,
    пластиковая труба — у каждой свой код» (сид включает системную трубу
    с 3 типами);
  - справка о механике (дословно): «если у семейства 5 типоразмеров и все
    имеют одинаковый код — нужно 5 раз заполнить одинаковый код в каждый
    типоразмер, только так это работает: Revit принимает код по
    классификатору на типоразмер; в спецификации беру поле "Семейство и
    типоразмер", сортирую по нему, чтобы все типоразмеры были разными
    строчками, и в каждую строчку заполняю код».
