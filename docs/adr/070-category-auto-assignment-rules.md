# ADR-070: Автоназначение категории при batch-импорте по правилам-условиям

**Date:** 2026-08-24  
**Status:** accepted  
**Related:** ADR-059 (Import Validation Gate), ADR-055 (family facts), ADR-064 (system family key), I-09, I-14, Issue #241

## Context

Пользователи просили автоназначение категории при batch-импорте: семейства
должны сами получать категорию каталога на основе условий над извлекаемыми
данными, без ручной раздачи через пикер. Ключевые ограничения из
обсуждения с владельцем:

- условия строятся только из **библиотеки атрибутов** (attribute_definitions,
  наполняется вручную) — база может быть пустой на момент настройки;
- правила НЕ зависят от binding'ов категории (unbind не должен их ломать);
- нужны системные поля: категория Revit, Part Type, имя семейства;
- нужны OR-группы AND-условий («Отвод ИЛИ Тройник», но «материал=сталь И
  категория=фитинги»);
- конфликт (2+ категории подошли) не должен решаться молчаливым приоритетом;
- автоназначение НЕ перебивает категории Existing/Duplicate и ручной выбор;
- автоназначение и гейт-валидация (ADR-059) не должны конфликтовать.

## Decision

### 1. Модель: OR-группы AND-условий (DNF)

`category_assignment_rule_groups` (OR) + `category_assignment_conditions`
(AND), schema **v31**. Условие — либо атрибут библиотеки (FK на
attribute_definitions, матчинг по имени параметра в снапшоте), либо
системное поле (`revit_category` ordinal / `part_type` fact key /
`family_name` / `system_family_key`). CHECK-констрейнт гарантирует
взаимоисключаемость. FK CASCADE на categories/attribute_definitions.

### 2. Движок: переиспользование FamilyValidationEngine

Pure Core `CategoryAutoAssignEngine`: атрибутные условия конвертируются в
`EffectiveValidationRule` и прогоняются существующим движком валидации —
идентичная семантика операторов, display-units-first, all-types AND.
Системные условия — отдельный evaluator по locale-invariant ordinal'ам.
Результат tri-state: `NoMatch` / `Matched` / `Ambiguous`.

### 2a. Специфичность: самое глубокое совпадение выигрывает

Когда подходят правила нескольких категорий, побеждает **самая глубокая**
в дереве каталога (глубина = число сегментов полного пути, передаётся в
движок из preloaded-путей). Правило на подкатегорию точнее правила на
родителя: правило родителя работает fallback'ом для семей, которые не
взяло ни одно подправило, — дублировать/уточнять его не нужно. `Ambiguous`
остаётся только для честных ничьих (соседние категории равной глубины);
в кандидатах показываются только категории максимальной глубины.

Правила **не наследуются** от родителей (скрытая связность, потеря
гибкости, DNF-комбинаторика). Вместо этого редактор подкатегории
предлагает кнопку «Взять условия родителя» — правила ближайшего
предка с правилами копируются как НОВЫЕ независимые строки (чисто
редакторский сахар, без рантайм-связи).

### 3. Ограниченный набор операторов

`AssignmentOperatorPolicy`: для атрибутов разрешены только 9 «позитивных»
операторов. `NotEquals`/`NotContains`/`IsEmpty` запрещены — отсутствующий
параметр удовлетворяет им в движке → ложные назначения («семейство без
Материала попало в категорию по Материал NotContains сталь»). Защита
трёхслойная: фильтр комбобокса редактора, skip при чтении репозитория,
невыполнение условия в движке.

### 4. Конфликт = явный UX, а не скрытый приоритет

`Ambiguous` оставляет строку в «Без категории»; кликабельная иконка ⚠ в
колонке «Категория» открывает пикер, отфильтрованный по подходящим
категориям (с подзаголовком). Иконка видна всегда, пока текущая категория
не входит в рекомендованные — включая Existing/Duplicate и «Без категории»:
категория не перебивается, но несовпадение подсвечивается.

### 5. Точка применения: диалог, до гейт-валидации

`RunInitialGateAsync`: гейт для строк с категорией → preload правил (один
раз на диалог, модальный диалог гарантирует неизменность) → назначение
eligible-строк (New + provenance None + не gate-blocked) на UI-потоке →
повторная гейт-валидация назначенных строк. Порядок «assign → validate»
делает правила автоназначения и правила валидации ортогональными.
`CategoryProvenance.AutoRule` — автоматический provenance, re-derived при
переименовании. Все три продакшн-точки конструирования диалога (файлы,
активный файл, выделенные элементы) передают сервис.

### 6. Хранение ordinal'ов, а не лейблов

Категория Revit и Part Type хранятся в `value_text` как инвариантные
ordinal-строки — правило «Категория = Фитинги трубопроводов» работает и на
RU, и на EN Revit (философия FHV3, ADR-056). Пикер показывает локализованные
лейблы через `IRevitCategoryLabelService` (reflection + fallback для
Revit 2019, см. known-workarounds).

### 7. Metadata package v4

Правила автоназначения едут в пакете по пути категории и имени атрибута
(переносимо между базами); импорт — append-only (существующие группы не
затираются), неразрешимые условия скипаются с предупреждением. Пакеты v1–v3
читаются без изменений; старый код игнорирует секцию `assignmentRules`.

## Consequences

- Пользователь настраивает правила в окне «Категории и атрибуты»
  (контекстное меню / иконка фильтра на узле) — редактор OR-групп с
  пикерами категории Revit и Part Type (plain ComboBox со встроенным
  TextSearch-поиском, как в Revit), визуал И/ИЛИ.
- Дерево категорий показывает трёхсостоятельную иконку (серый cog / серый
  check / оранжевый cog) — видно, у какой категории есть правила.
- Known limitation: кэш правил живёт на сессию batch-диалога (диалог
  модальный — редактирование правил параллельно невозможно).
- Known limitation: пикер «Категория Revit» предлагает курируемый список
  ~33 модельных категорий (MEP + типовые архитектурные, см.
  `RevitCategoryLabelService.ModelCategories`). Семья вне списка никогда
  не сматчит правило по RevitCategory — используйте PartType/FamilyName
  или атрибутные условия.
- Known limitation: сохранение правил не атомарно (последовательные
  repo-вызовы); сбой посреди оставляет частичное состояние, которое
  выравнивается повторным сохранением (diff против текущего состояния БД).
- Known limitation: переименование определения атрибута молча ломает
  name-based условия (наследуется от ADR-059).
- SystemFamilyKey поддержан движком, но скрыт из UI-редактора (нет
  user-friendly пикера); legacy-условия с ним скипаются при загрузке
  редактора с Warn.
