# ADR-068: E2 nested shared — механизм обновления в family-документе, верификация FHV8V, FHV9 phantom-значения, self-heal dependency links (#209)

**Date:** 2026-08-12
**Status:** accepted
**Related:** Issue #209 (E2), #207 (EPIC), ADR-066 (модель family_dependencies), ADR-066 §links, ADR-054/056/058 (актуализация/хэши/совместимость БД), ADR-029 (shared nested load)

## Context

E2 (#209) добавляет общие (shared) вложенные семейства как полноценные элементы
каталога: импорт из активного семейства (UC-2), dedup по контент-хэшу,
drift-бэйджи родителей, обновление вложенного «по месту» внутри открытого в
редакторе семейства. Реализация столкнулась с четырьмя неочевидными стенами,
каждая из которых стоила отдельного расследования (зонды + ручные стресс-тесты
владельца 2026-08-10/11/12). Этот ADR фиксирует принятые механизмы и их
обоснования — без них код выглядит «странно» и будет сломан при первом же
рефакторинге.

### Стена 1: `LoadFamily` не обновляет вложенное семейство

`Document.LoadFamily(path, IFamilyLoadOptions)` в family-документе — **SILENT
NO-OP** для семейства с расхождением lineage или малым diff'ом: Revit сравнивает
внутренний «changedness stamp» (dirty flag), а не контент. Колбэки firing, `true`
возвращается, embedded-дефиниция не меняется. Autodesk подтверждает: API не
повторяет ручной UI reload (Revit API forum, 2026-04-30). Доказано зондами
(`NestedFamilyReloadTests`, `RealLibraryNestedReloadReproTests`) на реальной
библиотеке владельца.

### Стена 2: верификация «приземлился ли контент»

Полный identity-хэш (FHV8) сравнивать нельзя: (a) embedded-дефиниция в хосте
регенерируется хостом (объёмы/bbox/длины отличаются законно), (b) **Revit НИКОГДА
не пропагирует группы параметров** ни на одном merge (API или UI) — embedded
навсегда хранит группировку хоста. Значения phantom-типов могут драйвиться
хостом через ассоциации — тоже не сравнимы с файлом.

### Стена 3: маркеры версий против хэш-дедупа

После обновления embedded-контент равен файлу новой версии по FHV8V, но его
identity-хэш (с группами хоста) продолжает совпадать со СТАРОЙ версией или ни с
чем — хэш-дедуп при импорте родителя врёт про версию вложенного.

### Стена 4 (стресс-тесты 2026-08-11/12): три production-бага

1. Title-guard load-сервиса ложно срабатывал на собственный background-документ
   (`ReferenceEquals` ненадёжен — Revit выдаёт разные managed-обёртки одного
   документа) → каждое реальное обновление фейлилось «is open in the Family Editor».
2. UC-2 фильтровал duplicate-строки вложенных до executor'а → новая версия
   родителя не получала dependency links → drift-бэйдж никогда не появлялся.
3. FHV8 пропускал phantom-тип целиком → значения безтиповых семейств выпали из
   хэша → ложный «Дубликат» при любой правке значений (напр. «Модель»).

## Decision

### 1. Poke + doc-to-doc merge (`RevitFamilyLoadService.ReloadNestedInFamilyDocument`)

Рецепт, рекомендованный Autodesk support и подтверждённый владельцем вручную:
открыть исходный .rfa в фоне → **net-zero in-memory poke** (добавить scratch
family-параметр, commit, удалить, commit+regen — два коммита, файл НЕ
сохраняется; stamp — dirty flag без истории контента, net-zero правка его
переворачивает) → `sourceDoc.LoadFamily(hostDoc, options)` **вне транзакции**
(doc-to-doc управляет своей; host не должен быть modifiable). Merge идёт по
полному overwrite-пути, дефиниция реально заменяется. Poke не удался → fallback
на path-load. `null` от doc-to-doc после успешного poke — жёсткий фейл без
ретрая (источник уже «грязный», path-load читает нетронутый файл и попадёт в тот
же no-op).

Depth-N: shared-вложенное на любой глубине существует как ОДНА hoisted-дефиниция
в host-документе — прямой reload в host обновляет именно её, и именно она
доезжает до проектов. Внутренняя EditFamily-копия промежуточного родителя
хранит устаревшую копию — косметика, из проектов недостижима (контракты
`NestedFamilyReloadTests`, 2026-08-10).

### 2. Два грейда хэша: identity (FHV9) vs verification (FHV8V)

> **ЗАМЕНЕНО (addendum 2026-08-12, §A1 ниже):** двухгрейдовая система
> упразднена в тот же день — зонд `DrivenEmbeddedPollutionProbeTests`
> опроверг ключевую предпосылку «хост загрязняет embedded-документ».
> Текущее состояние: единый хэш FHV10 (группы не хэшируются нигде).
> Текст ниже оставлен как история принятия решения — не как руководство.

- **Identity** (хранится в каталоге, дедуп/версии): включает группы
  параметров, метрики геометрии, значения типов и (FHV9) значения phantom.
- **Verification** (`ComputeForEmbeddedVerification`, эфемерный, НЕ хранится):
  исключает группы, regen-метрики (volumes/bounds/areas/длины/размеры и
  координаты коннекторов) и phantom-значения — всё, что физически не
  переносится merge'ем или драйвится хостом. Используется ТОЛЬКО для
  «приземлился ли контент файла в открытый family-документ» (pre-verify skip /
  арбитраж failed-reload / post-verify). Tri-state: `true/false/null`
  (неприменимо) — политика `StaleUpdateVerificationPolicy`.

Осознанное следствие: value-only правка phantom-вложенного не запускает reload
при «Обновить» (pre-verify совпадает → только маркер). Группы/phantom-значения
физически непроверяемы в embedded-контексте — принимаем как ограничение, а не
баг.

### 3. Marker-first резолюция версий

После успешной verify ES-маркер версии пишется на embedded-семейство; при
импорте родителя `EmbeddedMarkerMatchResolver` даёт маркеру приоритет над
хэш-дедупом (маркер — пост-верификационная истина). Хэш-дедуп остаётся
fallback'ом.

### 4. Single-open оркестрация + source-aware интерфейс

Цикл обновления (pre-verify → poke+merge → арбитраж → post-verify) идёт в ОДНОМ
`RaiseAsync` с одним `OpenDocumentFile` на семейство (было до 3). Updater
владеет документом и закрывает его; load-сервис получает его как **borrowed**
через `IFamilyLoadServiceSourceAware` (новый Core-интерфейс, наследует
`IFamilyLoadService`; `Func<Document?>?` провайдер) и не закрывает. Гарды
«файл открыт в редакторе»: Title-guard исключает borrowed-документ **по пути**
(ReferenceEquals ненадёжен — стена 4.1), PathName-guard пропускается (updater
проверил до открытия). Legacy-путь сохранён для не-source-aware реализаций
(моки) и проектного контекста.

### 5. Dependency links: dedup-link для skipped-children + self-heal

Executor получает ВСЕ строки вложенных (включая duplicate-skipped) — planner
записывает dedup-links (label = `MatchedVersionLabel`, т.е. с учётом
marker-override). **Self-heal**: родитель, пропущенный как Duplicate СВОЕЙ
ТЕКУЩЕЙ версии (контент идентичен), всё равно попадает в parent-map → его
текущая версия получает links из фактических вложенных. Это лечит версии,
импортированные до фикса (у них links=0 и drift невозможен в принципе), без
миграции БД. Existing+Skip (контент изменён, пользователь отказался) — НЕ
лечится: дети файла не описывают контент текущей версии.

### 6. FHV9: секция PHANTOM для безтиповых семейств

Значения phantom-типа извлекаются контекстно-стабильно: редактор/EditFamily —
текущий безымянный тип (Size=1); raw-открытие (Size=0, нет CurrentType) —
синтез `NewType("__SmartConPhantomValues__")` в транзакции с **RollBack**
(прецедент `ExtractGeometryPerType`, I-03b). Оба контекста читают одни дефолты
(зонд 2026-08-12). Секция — только в identity-грейде. Раскатка: критическая
задача `hash-v9` (пересчёт всех строк; NESTEDHASH транзитивно сдвигает хэши
предков), `DbCompatibility.CurrentMinPluginVersion` → `2.0.1-beta.9`.

## Consequences

### Положительные

- Обновление общих вложенных внутри редактируемого семейства работает
  end-to-end: reload → строгая verify → честный маркер → drift-бэйджи →
  marker-first при импорте. Ложный маркер невозможен по построению.
- Один `OpenDocumentFile` на семейство за цикл; меньше round-trips.
- Значения безтиповых семейств снова версионируются (регрессия FHV8 закрыта).
- База самолечится: hash-v9 (хэши) + self-heal (links) — без ручных миграций.

### Отрицательные / ограничения

- Группы параметров и phantom-значения не пропагируются merge'ем в embedded
  (ограничение Revit) → drift по ним не детектируется verify-грейдом; единый
  способ обновить группировку в хосте — удалить и загрузить заново (привязки
  потеряются) или пересобрать родителя.
- FHV9 — breaking data format: старые плагины не пишут в обновлённую базу
  (floor bump); первый запуск требует критической актуализации.
- Внутренняя EditFamily-копия промежуточного родителя (depth≥2) навсегда
  хранит устаревшую копию вложенного — косметика, из проектов недостижима.

### Отклонённые альтернативы

- **ReferenceEquals-исключение в guard'е** — ненадежно (стена 4.1), заменено
  PathName-исключением.
- **Включение phantom-значений/групп в FHV8V** — ложные фейлы верификации на
  host-driven контенте; отклонено зондом (nut group-only + flange regroup).
  **(ОТМЕНЕНО addendum'ом §A1: «host-driven контент» в embedded-документе
  не существует — phantom/метрики вернулись в хэш; группы исключены из
  identity тем же бампом, так что исключать их отдельно стало нечему.)**
- **Actualization-задача для dependency links** — тяжела (per-child dedup в
  контексте движка); self-heal при импорте покрывает тот же кейс бесплатно.
- **Сохранение phantom как типа `<default>`** (FHV3-7) — хэш зависел от
  контекста извлечения (raw Size=0 vs EditFamily Size=1), ломало дедуп.

## §A1. Addendum (2026-08-12, вечер): двухгрейдовая система упразднена — единый хэш FHV10 (#180)

Принятый в этот ADR дизайн «identity FHV9 (с группами) vs verification FHV8V
(без групп/метрик/phantom)» прожил один день и был заменён после двух
решающих зондов и продуктового решения владельца. ADR выше сохранён как
история; **текущее состояние — только этот раздел.**

### Зонд 1 (GroupPropagationProbeTests): группы не переносятся и poke-путём

Poke + doc-to-doc merge реально заменяет дефиницию (новый тип приземляется,
параметр в хосте пересоздаётся с новым ElementId), но группа параметра
остаётся хостовой — даже при in-place regroup'е источника
(`SetGroupTypeId`, та же идентичность параметра в файле). Ранее это было
доказано для UI-reload и plain merge (ручной тест владельца на гайке с
shared `ADSK_Материал обозначение`, 2026-08-11) — теперь и для poke-пути.
На Revit 2023 remove+add-вариант приземляет группу — но это семантика
«новый параметр», а не перенос группы существующего.

### Зонд 2 (DrivenEmbeddedPollutionProbeTests): «host pollution» не существует

Предпосылка вырезания метрик/phantom из verification-грейда («хост через
ассоциации переписывает embedded-документ») **опровергнута измерением**:
хост драйвит вложенное семейство через ассоциации INSTANCE-параметров,
которые живут на экземплярах в документе хоста (type-параметры shared
nested не ассоциируются даже в UI). EditFamily-документ вложенного хранит
авторское состояние байт-в-байт: при активном драйве (экземпляр в хосте =
999) полный identity-хэш embedded-копии равен файловому.

### Решение владельца: группы уходят из identity (FHV10)

Раз verification = «identity минус группы», а группы — единственное
непереносимое поле, двойная система покупалась ценой вечных противоречий
«маркер vs хэш» (P2: «Дубликат v2» на контенте с v1-группами). Владелец
принял: **группы параметров — не контент и не версионируются**
(обновить их в embedded всё равно нельзя). `FHV10|LOADABLE|` = FHV9 без
поля ParameterGroup; `ComputeForEmbeddedVerification` удалён — везде один
`ComputeForLoadable`. Сортировки унифицированы на детерминированных
topology-полях (H1). Пары версий «только группа» в существующих базах
после пересчёта получают один хэш — детерминировано (дедуп резолвит в
одну из них); marker-противоречия FHV8V-эпохи этой миграцией самолечатся.

Раскатка: критическая задача `hash-v10`. Floor `DbCompatibility` =
`2.0.1-beta.8` — первая бета, которая вообще выпускает форматы FHV8+
(последний тег на момент решения — v2.0.1-beta.7, v8/v9-хэши не
выпускались в релизных сборках). Константа никогда не должна превышать
версию, в которой она шипится: больший floor self-gate'ит release-сборку
после миграции (в DEBUG-сборках гейт выключен по умолчанию).

### Правило «Проверить» (#180, вариант B — полная контентная проверка)

Единый хэш сделал контентную проверку честной во всех контекстах. Правило
(`StaleDetector`, и batch, и single check; loadable, семейство-документ и
проект):

1. **Маркера нет** (свежий импорт их не пишет) → контентное
   доказательство против файла текущей версии (EditFamily + один
   OpenDocumentFile на файл за прогон — per-run кэш): совпало →
   not-stale + heal маркера; различно/неопределимо → stale.
2. **Маркер устарел** (label ≠ current) → stale БЕЗ открытия документов
   (быстро); реконсиляция — «Обновить» (pre-verify skip → маркер).
3. **Маркер совпал** → пере-проверка контентом: совпало → not-stale;
   **различно → stale с новой причиной `StaleReason.ContentDrift`**
   (локальные правки после записи маркера; «Обновить» вернёт каталожный
   контент, тултип честно предупреждает о потере правок); неопределимо →
   доверяем маркеру. Стоимость — осознанная: «Проверить» — глубокая
   операция по кнопке; DnD/«Загрузить» остаются маркерными и быстрыми.

Системные типы этим не покрыты: per-type контентное сравнение требует
per-type хэшей в БД (#179) — там маркер остаётся контрактом.

### Batch-диалог: пометка происхождения версии (спящая при FHV10)

Строка вложенного, чья версия резолвлена ES-маркером вопреки
identity-матчу (`EmbeddedMarkerMatchResolver`), помечается
`IsMarkerResolvedVersion` → статус «Дубликат (v2 — маркер)» + тултип.
При FHV10 противоречие структурно невозможно в штатных путях — пометка
оставлена как честный индикатор краевых случаев (внешняя правка БД,
purge версии). Сбрасывается при rename re-dedup.

## §A2. Addendum (2026-08-13): «стена» raw reload'а оказалась group-only-diff специфичной

Ручной тест 2026-08-12 переписал v2-файл гайки в тестовой библиотеке
владельца (update-flow сохранил merge-артефакт; появился v3), и сьют
упал: константные пины `NutV1Hash = NutV2Hash = 6846AC6F` перестали
соответствовать файлам (v1=6846AC6F стабилен, v2 стал 9BECB98C). Факт по
логу прогона: с существенно отличающимся входящим файлом даже **сырой
unpoked reload приземляет v2** (`nut after = 9BECB98C` = файловый v2) —
no-op «стена» из раундов 1-5 (#209) была специфична к контенту,
отличающемуся ТОЛЬКО группой параметров (Revit не считает такую замену
изменением), а не к самому семейству. Продукционный вывод не меняется:
poke + doc-to-doc остаётся принудительным путём для group-only-diff, а
post-verify — арбитром честности маркера. Тест переработан: пины
вычисляются живьём из файлов в Seed, старый wall-тест заменён на
`ReloadNestedV2_IntoRealFlangePair_RawReload_DecisiveOutcome` (precondition
«embedded == v1» как детектор дрейфа фикстуры + ассерт «исход однозначен»:
LANDED v2 | WALL, но никогда PARTIAL MERGE). См. также
`docs/family-manager/209-shared-nested-reload-investigation.md`
(корректировка 2026-08-13).
