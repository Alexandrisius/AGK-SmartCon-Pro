# ADR-077: Model entity search — BM25 по метаданным, без глобального индекса элементов

**Date:** 2026-11-18  
**Status:** accepted  
**Related:** ADR-076 (tool surface), ADR-075 (hybrid retrieval только для каталога тулов/навыков), [H1 runbook](../agent/00-strategy/initial-improvement-runbook.md), [harness-ideal-plan §3.3](../agent/00-strategy/harness-ideal-plan.md)

## Context

Агент упирается в дословные совпадения: «шаровые краны» не находят «Кран
шаровый», «арматура трубопроводов» требует точного имени категории, а
«вентиляторы на 1 этаже» — ручного перебора категорий. Нужен гибкий поиск по
сущностям модели, а не только `contains` по точному параметру.

Ограничения:

- в модели 200–500 тыс. элементов, с видами/уровнями/осями/спецификациями —
  до ~1 млн;
- полнотекстовый индекс всех элементов — сотни МБ, десятки секунд сборки и
  постоянная инвалидация; для интерактивного агента неприемлемо;
- BM25 по маленькому каталогу сущностей (категории, семейства, типы, уровни,
  виды, параметры) — единицы мегабайт и 1–3 секунды;
- vector search для **каталога тулов/навыков** — отдельное решение ADR-075
  (H6), и оно не должно применяться к содержимому модели.

## Decision

### 1. Новый эпик H1b: Model entity search

Эпик ставится **сразу после H1**, до памяти/навыков и до vector retrieval.
H1 не расширяется. H1b не переименовывает H2–H7.

Порядок: **H1 → H1b → H2 → H3 → H4 → H5 → H7 → H6 (vector последним)**.

### 2. Индексируем каталог, а не элементы

Индекс H1b содержит только:

- категории (OST + display name + алиасы);
- семейства и типы (имя, категория, количество экземпляров);
- уровни, виды, листы, шаблоны видов;
- определения параметров (имя, shared/built-in, storage type, категории).

Объём — 5–20 тыс. записей, in-memory BM25, кэш на документ. Полный индекс
элементов не строится.

### 3. Текстовый конвейер

- токенизация, lowercase, ё→е;
- русский Snowball-стеммер;
- словарь синонимов предметной области (кран/клапан/вентиль,
  вентилятор/фанкойл, арматура/фитинг);
- алиасы категорий («арматура трубопроводов» → `OST_PipeAccessory`,
  «оборудование» → `OST_MechanicalEquipment`);
- fuzzy/trigram для опечаток;
- BM25 по name/description/synonyms, с boost на точное имя.

### 4. Tool surface

Один generic read-tool по ADR-076:

`search_model_entities(query, kinds:["family","type","category","level","view","parameter"], limit)`

Возвращает:

- `matches[]` — kind, name, id, category, count, parameter metadata;
- `resolved` — categoryIds / typeIds / levelIds для `query_elements`.

Поиск элементов остаётся структурным: `query_elements` с resolved-фильтрами.
Никаких per-family/per-property tools.

### 5. Ленивый индекс элементов — только как исключение

Если нужен поиск по произвольному тексту элемента:

- один параметр × одна категория за раз;
- сборка чанками на Revit-потоке, прогресс, отмена;
- кэш `documentId + categoryId + parameterName`, TTL и memory cap;
- инвалидация по `DocumentChanged` (added/modified/deleted);
- никогда не «весь документ целиком».

### 6. Document lifecycle

- ключ кэша — `documentId + fingerprint` (путь/UniqueId/версия);
- при смене документа — сброс;
- при `DocumentChanged` — инкрементальное обновление или инвалидация;
- сборка на Revit-потоке через `IExternalEventHandler` (I-01), без фоновых
  вызовов API.

### 7. Границы

- H1b ищет сущности **открытого документа**. Каталог FamilyManager (SQLite) —
  отдельная задача, если понадобится.
- Vector/embeddings по элементам модели не планируются: для модели —
  structural query + BM25-каталог.
- H6 (vector) остаётся последним инфраструктурным эпиком и относится только к
  каталогу тулов/навыков.

## Metrics / acceptance

- 100–200 реальных BIM-фраз: top-1 ≥80 %, top-5 recall ≥95 %, false match <5 %.
- Сборка каталога ≤3 с, память ≤20 МБ, поиск p95 <100 мс.
- Эталонные запросы: «кран шаровый волк», «шаровые краны на 2 этаже»,
  «вентиляторы на 1 этаже», «виды в папке Сводные».
- «Шаровые краны» находят «Кран шаровый»; «арматура трубопроводов» резолвится
  в `OST_PipeAccessory`.
- 0 глобальных индексов элементов; ленивый индекс — с cap и отменой.

## Consequences

- H1b даёт пользовательскую ценность сразу после H1, без vector-инфраструктуры.
- H1 остаётся в текущем объёме; model search не размывает его acceptance.
- H6 переносится в конец: vector нужен для 500–1000 тулов/навыков, а не для
  модели.
- H7 (typed facade/code mode) может идти до H6: длинный хвост важнее, чем
  vector для каталога тулов.
- Появляется общий `Bm25Index<T>` и `TextNormalizer` в Core — их же использует
  H1 и H6, дублирования нет.
