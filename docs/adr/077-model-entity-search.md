# ADR-077: Живой поиск по сущностям модели — без постоянного индекса

**Date:** 2026-11-18  
**Status:** accepted  
**Related:** ADR-076 (tool surface), ADR-075 (hybrid retrieval только для каталога тулов/навыков), [H1b–H1d plan](../agent/archive/00-strategy/h1b-tool-packs.md), [harness-ideal-plan §3.3](../agent/archive/00-strategy/harness-ideal-plan.md)

## Context

Агент упирается в дословные совпадения: «запорный вентиль» не находит
«Клапан запорный», «арматура трубопроводов» требует точного имени категории, а
«вентиляторы на 1 этаже» — ручного перебора категорий.

При этом модель — **живая и многопользовательская**:

- 200–500 тыс. элементов, до ~1 млн с видами/осями/спецификациями;
- 100 тыс. экземпляров одной категории с разными значениями параметра
  (`ТДСК_Наименование` и т.п.);
- модель меняется каждые несколько минут;
- 5 владельцев/сессий, worksharing central;
- имена семейств в библиотеке — короткие технические идентификаторы
  (`KR_SHAR_VOLK_15`), поисковый текст живёт в описании и общих параметрах.

Постоянный BM25/полнотекстовый индекс по такой модели — неправильная
архитектура: он устаревает между запросами, требует пересборки, не
разделяется между владельцами и плохо масштабируется на 1M элементов.

## Decision

### 1. Никакого постоянного индекса модели

Запрещены:

- BM25/Lucene/FTS-база по экземплярам модели;
- глобальный индекс «все элементы × все параметры»;
- пересборка индекса по расписанию;
- локальная индексная БД, которая живёт дольше одного запроса/хода.

Причина: модель меняется быстрее, чем индекс успевает остыть; при 5 владельцах
локальный индекс одного процесса нерелевантен остальным.

### 2. Поиск = нормализация запроса + живые структурные фильтры

Пайплайн:

1. **Нормализация на лету:** токенизация, lowercase, ё→е, русский Snowball-
   стеммер, синонимы (кран/клапан/вентиль, вентилятор/фанкойл,
   арматура/фитинг), алиасы категорий («арматура трубопроводов» →
   `OST_PipeAccessory`, «оборудование» → `OST_MechanicalEquipment`).
2. **Живые справочники:** `list_categories`, `list_levels`, `list_family_types`,
   `list_parameters` — маленькие выборки, читаются на месте.
3. **`find_families_with_parameter(name)`** — живой проход по семьям/типам
   (5–20k), без индекса.
4. **`query_elements`** — категория + уровень + условия по параметрам;
   добавляется `parameterContainsAny` (OR по вариантам стемминга/синонимов) и
   `matchedParameter`/`matchedValue` в результате.
5. **Ранжирование** — по числу/точности совпавших токенов в пределах уже
   найденной выборки, без индекса и без глобального скоринга.

### 3. Срез вместо всей модели

Запрос всегда сужается:

- категория (обязательно для текстового поиска),
- уровень/вид/тип — если известны,
- параметр — если известен; иначе `list_parameters(category)` или
  `get_element_details` по выборке.

Для 100k экземпляров одной категории это один живой проход с
`ElementParameterFilter`/`FilterStringContains` (или OR по вариантам). Если
замер покажет p95 выше допустимого, допускается **one-shot in-memory map на
время запроса** — не постоянный индекс, не БД.

### 4. Кэш — только на запрос/ход

- `documentId + fingerprint` (для проверки актуальности);
- результат живёт до конца хода/запроса;
- при `DocumentChanged` — сброс;
- никакой персистентности между сессиями.

### 5. Tool surface

- `list_family_types(category?, nameContains?, includeParameters?)` — живые
  семейства/типы, включая не размещённые;
- `find_families_with_parameter(parameterName)` — где параметр определён;
- `list_parameters(category?)` — какие параметры вообще есть (для выбора
  условия);
- `query_elements` + `parameterContainsAny` — экземпляры по значению;
- `summarize_parameter_values(category, parameter)` — частоты/уникальные
  значения для анализа 100k имён (живой проход, без индекса).

Никаких per-family/per-property tools (ADR-076).

## Performance / acceptance

- 100k экземпляров одной категории: один scoped-проход, p95 измерить;
  целевой ориентир — единицы секунд, не минуты.
- 5–20k семейств/типов: `find_families_with_parameter` ≤1–2 с.
- Если проход по 100k стабильно >5 с — one-shot in-memory map на запрос;
  постоянный индекс всё равно не вводится.
- 100 реальных BIM-фраз: правильная сущность найдена за ≤2 tool-вызова,
  false match <5 %, task success ≥80 %.
- Эталон: `KR_SHAR_VOLK_15` с `ТДСК_Наименование` = «Запорный вентиль ВОЛК»
  находится по «запорный вентиль волк» без имени файла.

## Consequences

- Нет stale-индекса, нет reindex, нет проблем с 5 владельцами/workshared.
- Поиск всегда по актуальной модели; цена — живой проход по срезу.
- H1b становится проще: нормализация + живые справочники + расширение
  `query_elements`, без инфраструктуры индекса.
- Vector/embeddings по модели не планируются (H6 — только каталог тулов/навыков).
- `search_model_entities` как BM25-каталог **не реализуется**; вместо него —
  живые `list_family_types`/`find_families_with_parameter`/`query_elements`.
