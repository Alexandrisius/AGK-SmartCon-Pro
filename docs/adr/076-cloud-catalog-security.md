# ADR-076: Cloud Catalog Security & Credentials — аккаунты, токены, ключи доступа

**Date:** 2026-08-25  
**Status:** proposed  
**Related:** ADR-075 (Cloud Architecture), ADR-077 (Multi-author sync), ADR-022 (локальная RBAC — контрастная модель), roadmap §15 (риски: токены, IP)  
**Implements:** backlog ADR-FM-009 «Security and credentials»; tech-stack §6.6 (Credentials)  
**Детальный план:** [`docs/family-manager/02-plans/cloud-catalog-master-plan.md`](../family-manager/02-plans/cloud-catalog-master-plan.md)

## Context

Облачный каталог вводит серверную авторизацию — то, что ADR-022 сознательно
отклонила для локального offline-first сценария (там: `UserId={user}@{machine}`
без паролей). Требования владельца:

- публикация и подписка из плагина, без браузера на каждый чих;
- платные каталоги: доступ по **ключу**, который покупается у автора каталога
  (продажа — вне платформы на первой фазе, платформа не merchant of record);
- отзыв доступа должен быть возможен точечно;
- токены не хранятся в plaintext на диске (roadmap §15);
- клиент — net48 (R19–R24) и net8 (R25+), корпоративные прокси.

Исследование моделей лицензирования (Keygen, Lemon Squeezy, Gumroad license
API): индустриальный стандарт — ключ активируется один раз → клиент получает
долгоживущий токен → периодическая валидация → offline grace period → отзыв
ключа прекращает обновления, но не отбирает скачанное.

## Decision

### 1. Два контура идентичности

**Локальная RBAC (ADR-022) не меняется** и не смешивается с облачной. Облачная
идентичность — отдельная модель: аккаунт SmartCon Cloud (email + пароль) на
**ASP.NET Core Identity** — самопальная auth (свой PBKDF2/Argon2-хэшер, свои
сессии) запрещена: риск криптографических и session-ошибок перевешивает
экономию на зависимости; Identity даёт lockout/throttling/подтверждённые
практики из коробки. Дополнительно: throttling на register/login (per-IP),
ответы регистрации не раскрывают занятость email (единая формулировка),
ротация JWT signing keys (два активных ключа, overlap-период) — минимум на C1.

Роли на каталоге (серверные, не путать с `db_users`): `Owner` (владелец
каталога), `Editor` (со-автор, ADR-077), `Subscriber` (по ключу).

### 2. Токены плагина

- Автор/редактор аутентифицируется **один раз** в диалоге «Аккаунт SmartCon
  Cloud» → сервер выдаёт пару **JWT access (короткий, 15–60 мин) + refresh
  (30–90 дней, rotating)**. Refresh-rotation: каждое обновление инвалидирует
  предыдущий refresh (детект кражи по reuse → инвалидация всей цепочки).
- **JWT несёт только userId + expiry. Роли, подписки, статусы ключей в claims
  НЕ кладутся**: авторизация — per-request по PostgreSQL (indexed lookup,
  пренебрежимая нагрузка). Это закрывает мгновенность: снятие роли Editor,
  отзыв ключа, suspend подписки, unpublish — без ожидания TTL access-токена.
  Subscription-check выполняется на **всех** catalog-scoped эндпоинтах
  подписчика (manifest latest/{seq}, files/resolve, checkin), не только resolve.
- Для автоматизации (ночная публикация по расписанию) — **PAT**
  (Personal Access Token, scope `publish:catalog:{id}`, revocable, с
  `expiresAtUtc`, `lastUsedAtUtc`). Scope-enforcement — whitelist middleware:
  PAT не может ничего, кроме publish своего каталога (управление ключами,
  редакторами, настройками — только интерактивная сессия).
- **Хранение на клиенте: Windows Credential Manager** через
  `Meziantou.Framework.Win32.CredentialManager` (актуальная линия 3.x,
  Win32 CredRead/CredWrite; совместима с net48 и net8 — верифицировано
  2026-08-25). Target name: `AGK.SmartCon.Cloud:{endpoint}:{accountId}`.
  Абстракция `ICredentialStore` (Core) → реализация `Win32CredentialStore`.
  Запрещено: plaintext в `%APPDATA%`, в реестре, в `appsettings`.
- **Компрометация signing key:** ключи подписи — в Docker secrets (не в
  образе/репозитории); штатная ротация — два активных ключа с overlap;
  аварийная — ротация без overlap + опциональная инвалидация всех
  refresh-цепочек (force re-login). Процедура — runbook в `server/docs/`.

### 3. Ключи доступа к каталогу (монетизация)

- Ключ — строка вида `SCCAT-XXXX-XXXX-XXXX-XXXX` (Crockford base32, ~80 бит
  энтропии; генерация `RandomNumberGenerator`). На сервере хранится **только
  SHA-256 хэш ключа** (как пароль); plaintext показывается автору один раз.
- Запись ключа: `{keyHash, catalogId, label, createdBy, expiresAtUtc?,
  maxActivations?, status: active|revoked}`.
- **`maxActivations` по умолчанию = 1** (индустриальный стандарт «1 ключ =
  1 активация»); безлимит — только явный выбор автора с подтверждением в UI.
  Проверка лимита — внутри сериализуемой транзакции активации (гонка двух
  одновременных subscribe с лимитом 1 решается БД, не кодом).
- **`expiresAtUtc` ключа = дедлайн АКТИВАЦИИ** (после него ключ нельзя
  активировать); на уже созданные подписки не влияет. Подписка живёт до
  отзыва/отписки; «временная подписка» — отдельное поле
  `subscriptions.expires_at_utc` (post-MVP, не путать с ключом).
- **Выпускает автор** из плагина (вкладка «Доступ»): создать / отозвать /
  переименовать метку. Rate limit создания: 100 ключей/день/каталог (антиспам).
- **Активация подписчиком:** «Подключить облачный каталог» → endpoint +
  slug + ключ → `POST /catalogs/{slug}/subscribe` → сервер валидирует ключ →
  создаёт `subscriptions` запись → выдаёт subscriber JWT. При subscribe
  платного/любого каталога фиксируется **согласие**: «ваш email будет виден
  автору каталога» (ПДн, основание передачи; см. §7).
- **Отзыв ключа** — массовая мера: прекращает sync всех подписок ключа.
  **Точечная мера** — `POST /subscriptions/{id}/suspend` (Owner, по нарушителю,
  с reason). Оба действия пишутся в append-only аудит
  (`access_key_events`/`subscription_events`: actor, action, at_utc, reason) —
  логи платформы — единственное доказательство в спорах «автор отозвал после
  оплаты».
- Отзыв/suspend не отбирает уже скачанное (файлы физически у пользователя),
  но прекращает **будущие sync**. Семантика фиксируется в UI автора и оферте.
- Опционально per-catalog: `checkInIntervalDays` (по умолчанию 30, opt-in
  автора) — sync платного каталога требует онлайн-валидации не реже интервала;
  после истечения — sync блокируется до валидации, **локальная копия работает
  read-only бессрочно** (grace-модель Keygen, адаптированная). UX обязан
  объяснять это при subscribe («обновления требуют интернета раз в N дней,
  контент работает всегда») + Warn за 3 дня до истечения grace.

### 4. Авторизация скачивания файлов (главная дыра таких систем)

`/files/resolve` (батч SHA-256 → presigned URL) обязан:

1. Резолвить каждый запрошенный хэш к каталогам, где этот объект используется
   (таблица `cas_objects` ↔ `publish_point_files`).
2. Проверять **активную подписку или editor/owner роль на КАЖДЫЙ** такой
   каталог. Хэш из чужого платного каталога без подписки → попадает в
   `unavailable` (остальные резолвятся).
3. Presigned URL — GET-only, TTL 15 минут, на конкретный object key.
4. Rate limit на resolve (защита от перебора) + audit log `download_events`.

**Анти-оракулы (фиксируем с первого дня):**

- Для запросов без доступа к private-каталогу — **всегда 404 на ВСЕХ
  `{slug}`-эндпоинтах** (карточка, subscribe, manifest, keys и т.д.); 403
  раскрывает существование slug (slug человекочитаем и перебираем).
- `/files/resolve` возвращает единый список `unavailable` = denied ∪ not-found
  (отдельный `denied` раскрывал бы «файл существует в чужом каталоге»).
- **Манифест не содержит PII:** `publishedBy` в манифесте и на версиях —
  `displayName` (псевдоним по оферте), никогда email и никогда `user@machine`
  локальной RBAC. Email виден только в Owner-only API (карточка каталога
  владельца, список подписчиков — с согласия подписчика, §3). При удалении
  аккаунта исторические манифесты перезаписываются GC-задачей
  (displayName → «deleted user»; манифесты маленькие, перезапись дёшева).
  `CatalogManifestBuilder` обязан фильтровать локальные identity/пути.

**Accepted risk (зафиксирован):** presigned URL живут 15 минут — в это окно
отозванный подписчик может передать живые URL третьим лицам (E5). TTL и есть
митигация; меньший TTL ломает долгие докачки на слабых каналах.

### 4a. Квоты и анти-абuse upload (C1-обязательно)

Свободная регистрация + presigned PUT без квот = бесплатный файлохостинг за
наш счёт. Обязательный минимум (значения — конфигом):

- per-object max size (constraint Content-Length в presigned PUT);
- per-user storage quota (сумма по `cas_objects` владельца через
  `publish_point_files`; дефолт — 5 ГБ, поднимается владельцем платформы);
- лимит одновременных pending-uploads и rate limit на `publish/prepare`;
- rate limit на создание ключей (§3) и на `subscribe` (per-IP и per-user).

**Целостность CAS — полная, не spot:** клиент при upload обязан передавать
`x-amz-checksum-sha256` (поддержка AWSSDK.S3); сервер при publish/commit
сверяет checksum **каждого** объекта с декларированным `sha256` манифеста.
Один непроверенный объект — отравленный кэш у всех подписчиков всех каталогов,
шарящих хэш через CAS-дедуп.

**Контентная гигиена:** при commit — magic-bytes валидация (`.rfa`/`.rvt` =
OLE CFB signature; assets — whitelist расширений/MIME). Антивирус — не MVP;
ответственность за содержимое семейств — на авторе по оферте + reports (§7).

Запрещено: отдавать файлы по «угадываемым» URL без проверки; хранить
долгоживущие presigned URL на клиенте.

### 5. Канал и net48-совместимость

- Только HTTPS. Фаза 0: TLS терминирует Cloudflare (tunnel), сервер за
  туннелем — plain HTTP на localhost (стандартная модель Cloudflare Tunnel).
- Клиентский HTTP — по образцу `GitHubUpdateService`: `HttpClient` с
  `ServicePointManager.ReusePort`/SecurityProtocol хаками для net48, retry ×3
  на transient, прогресс, таймауты. TLS 1.2+ принудительно на net48 через
  `ServicePointManager.SecurityProtocol` (известный net48-default нюанс).
- Диагностика корпоративных прокси/SSL-инспекции: понятная ошибка
  «проверьте прокси/сертификаты», Warn с `[Action: ...]` (правило L9).

### 6. Что осознанно НЕ делаем на MVP

- OAuth-соцсети (Google/SSO) — C6.
- Machine fingerprinting / node-lock лицензии — избыточно для каталогов;
  `maxActivations` на ключе достаточно.
- Шифрование контента at-rest поверх R2 — контент семейств не персональные
  данные; платность защищается авторизацией выдачи, а не шифрованием блобов.
- Встроенные платежи — фаза маркетплейса (C5), отдельное юридическое ТЗ.

### 7. Персональные данные (ФЗ-152) — закладывается в схему C1

- **Бэкапы PG шифруются ДО отправки** в R2 (`pg_dump | age → R2`): R2 хранит
  только шифротекст → трансграничной передачи ПДн в открытом виде нет.
  Прохождение трафика через Cloudflare (US-процессор) отражается в политике
  конфиденциальности (C5, юр. блок).
- `cloud_users`: `deleted_at_utc` (soft-delete), `consent_version` /
  `consent_at_utc` (фиксация согласия при register). При удалении аккаунта:
  анонимизация PII-полей (email → хэш-tombstone), `download_events.user_id`
  → NULL, исторические манифесты перезаписываются (§4); владелец с живыми
  каталогами обязан сначала удалить/передать каталоги.
- Согласие подписчика на видимость email автору — при subscribe (§3).
- Сервер фазы 0 физически в РФ (домашний ПК владельца) — локализация ПДн
  соблюдается; при переезде на VPS — РФ-регион (или пересмотр политики).

### 8. Анти-абuse витрины (схема C1, UI — C5)

Уже в схеме C1 (нулевая стоимость сейчас, дорого задним числом):
`reports(id, catalog_id, reporter_user_id, reason, created_at_utc)` и
`catalogs.moderation_status` (`ok|hidden|verified`). Гейт публичной витрины:
подтверждённый email + account age N дней + лимит публичных каталогов на
аккаунт; `verified` — ручной флаг платформы против impersonation брендов.
Статистика автора/витрины считается как **distinct users за окно**, не сырые
`download_events` (антинакрутка). `description` — plain text only (без
HTML/Markdown, XSS-вектор), ссылки некликабельны на веб-странице каталога.

## Consequences

- Кража refresh-токена детектируется rotation-reuse → инвалидация сессии.
- Отзыв ключа обратимо для пользователя: автор может выдать новый ключ;
  повторный `subscribe` тем же аккаунтом — **идемпотентен** (restore
  существующей подписки, активацию не потребляет) — переустановка ОС/новая
  машина не сжигает ключ с `maxActivations=1`.
- **Email-инфраструктура — C5, не C1.** Подтверждение email, self-service
  reset пароля и transactional-письма откладываются до маркетплейса (выбор
  SMTP/transactional-сервиса — тогда же). Обоснование: корпоративный сценарий
  S1 (C1–C4) живёт на сервере владельца платформы, аккаунты создаются
  осознанно, reset — ручной операцией владельца сервера. Гейт витрины
  «подтверждённый email» (§8) актуален с C5 — к этому моменту почта есть.
  Зафиксировано, чтобы C1 не угадывал.
- Подписчик без сети > checkInInterval — локальная копия работает, sync нет:
  офлайн-работа не ломается никогда.
- Переезд сервера (дом → VPS) не трогает токены: endpoint в Credential Manager
  key — но если endpoint сменится, требуется повторный вход (принято: endpoint
  фиксируем через домен с первого дня).
- Known limitation: email+пароль — базовая политика Identity (минимум длины,
  throttling логина); подтверждение email и восстановление пароля — **C5**
  (см. Consequences), до C5 reset — ручная операция владельца сервера.
- Known limitation: подделываемость `user@machine` локальной RBAC (ADR-022)
  на облако не переносится — облачные права только по серверным токенам.

## Verification

- C1: penetration-чеклист (перебор хэшей в /files/resolve, reuse refresh,
  revoked key sync, expired presigned URL).
- Клиент: unit-тесты `Win32CredentialStore` (mock Win32), `CloudAuthService`
  (refresh rotation, grace). Ручной тест: net48 Revit 2023 за корпоративным
  прокси (по возможности) + две машины автора.
