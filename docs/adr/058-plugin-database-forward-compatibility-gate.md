# ADR-058: Plugin↔Database forward-compatibility gate (min_plugin_version)

**Date:** 2026-07-28  
**Status:** accepted  
**Related:** Issue #173, ADR-021 (SemVersion), ADR-054 (actualization engine), ADR-056 (FHV3), I-14

## Context

Общая база FamilyManager (SMB-шара) используется командой с разными версиями
плагина. Реальный инцидент: Owner обновил плагин (beta.4 → beta.5) и выполнил
актуализацию базы (hash-v3, ADR-056). Остальные пользователи на старом плагине
продолжили работать с обновлённой базой без какого-либо уведомления.

Доказанный вред: дедуп старого плагина (FHV2) фильтрует
`hash_format_version = 2`, в обновлённой базе все хэши `3` → hash-first поиск
молча «не находит» дубликаты → импорт создаёт молчаливые дубликаты в общей
базе. DDL-мигратор старого плагина на `schema_version=23` делает молчаливый
no-op — сигнала «база новее плагина» не существовало.

Просмотр/дерево/свойства безвредны — опасна только запись (импорт/изменения).

Индустриальный прецедент — паттерн «min reader version»:
`SQLiteOpenHelper.onDowngrade` (Android) по умолчанию **отклоняет** открытие
базы новее версии приложения; Rails/Flyway ошибаются на неизвестной более
новой миграции. Молчаливая работа старого кода с новым форматом хуже
честного отказа.

## Decision

### 1. Маркер: `database_meta.min_plugin_version` (миграция V24)

Минимальная версия плагина, способная безопасно **писать** в базу. `NULL` —
нет ограничения (legacy-базы). V24 дополнительно ретро-гейтит базы, уже
несущие FHV3-хэши (`hash_format_version = 3`), на `2.0.1-beta.5` — первый
FHV3-совместимый релиз.

Новые базы (`CreateDatabaseAsync`) пишут floor
`DbCompatibility.CurrentMinPluginVersion` сразу — они с рождения в текущем
breaking-формате.

### 2. Проверка: `IDatabaseCompatibilityService`

На connect/switch/init (перед резолвом RBAC-роли) читает маркер и сравнивает
с версией плагина (`IUpdateService.GetCurrentVersion` → `SemVersion`,
ADR-021). **Fail-open**: отсутствующий/битый/нечитаемый маркер никогда не
блокирует — гейт только при доказанно более новом floor.

### 3. Реакция на гейт: баннер + ярусный read-only (не жёсткий блок)

Гейт защищает **целостность каталога**, а не ограничивает пользователя «на
всякий случай». Поэтому модель ярусная:

**Блокируется — всё, что пишет в catalog.db** (импорт, удаление, свойства,
версии, ассеты, EditFamily, управление пользователями, конвертация типа базы):
- Центральная точка: `DbAccessControlService.CanImport/CanEdit/CanManageUsers`
  AND'ят `IsDatabaseNewerThanPlugin` — все app-level предикаты (панель,
  диалог свойств через `isReadOnly: !CanEdit`, движок актуализации)
  получают гейт бесплатно, без дублирования проверок по точкам вызова.
- Физический слой: `ApplyWriteAccess` AND'ит флаг в `SetWriteAccess`
  (`Mode=ReadOnly`) — defense in depth, запись упадёт даже при обходе UI.
- UX зеркалит роль Engineer: запрещённые команды скрыты/disabled.

**Разрешается — использование каталога на чтение:**
просмотр/поиск/3D/свойства и **загрузка семейств в проект** (LoadToProject,
DnD, PlaceType, UpdateStale). Эти операции читают путь к managed `.rfa` и
пишут только в `.rvt`-проект (семейство, ES-маркер версии) — catalog.db
остаётся нетронутым, поэтому устаревший плагин не может ничего испортить.
Гейт актуализации (`DatabaseUpdateStateService.EnsureUpToDateAsync`)
намеренно НЕ расширен compat-проверкой: его домен — stale-данные ADR-054,
добавление туда compat-гейта ломало бы tiered-модель и создавало второй,
несогласованный центр принятия решений.

**Баннер:** «База данных обновлена до более новой версии SmartCon ({min}).
Текущая версия приложения устарела: просмотр и загрузка семейств в проект
доступны, но изменение базы недоступно» + кнопка **«Обновить приложение»** →
существующее окно About через `IAboutDialogService` (Core → App).

**Баннер адресован только пишущим ролям** (`IsEditorRole` = Owner/BimMaster
без compat-AND'а, `ShowPluginGateBanner = gated && IsEditorRole`): для
Инженера гейт ничего не меняет — его роль и так read-only, а баннер был бы
бессмысленным шумом и давлением «качай бету» на тех, кто навредить не может
в принципе.

**Предупреждение обновляющего:** первый редактор, запускающий критическое
обновление, делает информированный выбор — диалог «Обновить сейчас?»
дополнен строкой «после обновления пользователи со старыми версиями SmartCon
не смогут редактировать эту базу (просмотр и загрузка в проект останутся
доступны)». Это стандартный паттерн shared versioned resource (Figma/Docs):
breaking-переход виден инициатору до точки невозврата, остальные
деградируют мягко (read-only + кнопка обновления), никто не «заставлен»
качать бету — без обновления теряется только запись, не работа.

Баннер/точка/команда «Обновить базу» (ADR-054) подавляются: гейтированный
плагин не может выполнить обновление, показ альтернативного гейта запутает.

**Почему не полный запрет (как у гейта актуализации):** гейт ADR-054 висит
минуты и снимается кнопкой «Обновить базу» здесь же; compat-гейт держится до
обновления приложения у пользователя (дни) — блокировка ежедневной работы
(расстановки семейств) была бы реальным вредом для команды, не покупая
ничего: целостность каталога уже гарантирована ярусом записи.

### 4. Конвенция для будущих breaking-изменений

Breaking-изменение данных (новый формат хэша, смена семантики колонок) =
два действия в одном PR:
1. bump `DbCompatibility.CurrentMinPluginVersion` на первый релиз с этим
   изменением;
2. миграция с backfill `min_plugin_version` из маркера в данных, доказывающего
   применение изменения (прецедент V24: `hash_format_version = 3`).

Не-breaking изменения (аддитивные колонки/таблицы, опциональные артефакты)
floor не поднимают.

## Отклонённые альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Жёсткий блок подключения | Просмотр безвреден; запрет мешает даже открыть каталог. Read-only даёт тот же уровень защиты записи при меньшей враждебности. |
| Только баннер без гейта | Не защищает от молчаливых дубликатов при импорте. |
| Объявление breaking на уровне задач актуализации (`IDatabaseActualizationTask.MinPluginVersionAfterApply`) | Знание централизовано в миграторе — единственной точке, исполняемой при каждом подключении любой версией с гейтом; per-task декларации размазывают конвенцию. |
| Ретро-гейт уже установленных старых версий | Невозможно: кода гейта в них нет. Закрывается коммуникацией (changelog + уведомление команды) для текущего перехода; гейт решает все будущие. |

### 5. Escape hatch для разработчика (dev-билды)

Локальная dev-сборка берёт версию из `Version.txt` (напр. `2.0.0`), которая
старше любого beta-floor — без послабления разработчик был бы гейтован на
собственных базах после каждой пересборки. Механизм послабления:

- **DEBUG-билд: гейт выключен по умолчанию.** Разработчик-владелец работает
  свободно; suppress-случай пишется на уровне Debug в лог.
- **`SMARTCON_FM_COMPAT_GATE=force`** — включает гейт обратно в DEBUG-билде
  (тестирование самого гейта без пересборки).
- **`SMARTCON_FM_COMPAT_GATE=disable`** — аварийный выключатель даже в
  RELEASE (support-сценарий); suppress гейтованной базы пишет Warn с
  `[Action: remove ...]`, чтобы override никогда не забывался включённым.
- Реализация: `OverrideMode` в `DatabaseCompatibilityService` (public ctor
  читает env, internal ctor с явным override — тестовый шов; тесты
  детерминированы и не зависят от flavor сборки).

## Consequences

- Команда с общей базой получает честный сигнал «обновись» вместо молчаливой
  порчи каталога; устаревший плагин работает как Engineer (просмотр + загрузка
  в проект), без риска записи.
- Цена нового breaking-изменения — константа + одна миграция с backfill.
- `IAboutDialogService` — первый канал из feature-модуля в About; пригоден и
  для будущих «обновитесь» сценариев.
- Известное ограничение: защита действует с релиза, содержащего гейт
  (установленные beta ≤6 кода гейта не имеют).
- Dev-билды по умолчанию не защищены (осознанно, §5) — защита production
  проверяется RELEASE-сборкой или `SMARTCON_FM_COMPAT_GATE=force`.
