## Context

Системные «семейства» каталога FamilyManager — мини-проекты (.rvt) с типами труб, воздуховодов, стен и др. (14 категорий `SystemCategoryRegistry`). До этого ADR загрузка типа в проект работала через `ElementTransformUtils.CopyElements`, который **не умеет перезаписывать существующий тип** (подтверждено Autodesk, wishlist CF-882/CF-4242 с 2014 г.): при совпадении имени DnD молча активировал старый тип, «Загрузить в проект» ничего не делала, а попытки обойти это плодили дубликаты («Тип (1)», «Материал 1», дубли сегментов и фитингов). Из-за отсутствия механизма обновления для системных типов не существовало stale-индикации и команды «Обновить».

Штатная команда Revit «Передать стандарты проекта» перезаписывать умеет, но: нет API (заявка с 2016 г.), работает только целыми группами стандартов, имеет задокументированные баги с материалами. Поведенческий эталон для нас — её семантика «Заменить»: тип обновляется на месте, размещённые экземпляры подхватывают изменения.

## Decision

### 1. Полный отказ от CopyElements для синхронизации — запись данных вместо копирования

Для существующего типа копирование бесполезно по определению, а раз ручная запись неизбежна — она становится **единым механизмом «создать или обновить»** для всех точек входа:

- Тип есть в проекте → его данные перезаписываются эталоном (параметры, слои, трассировка).
- Типа нет → создаётся `Duplicate()` любого существующего типа-болванки той же категории + запись эталонных данных. Кейс «в проекте нет ни одного типа категории» признан невозможным (всегда есть шаблонный), но охраняется (`NoPrototypeType` + Warn).

Убирая копирование, убираем целый класс загрязнений проекта: ноль дубликатов типов, материалов, сегментов, спецификаций, фитингов — жёсткое требование приёмки.

### 2. Мини-проект — единственный эталон; чтение живьём, БД не меняется

Вариант «полный снимок эталона в SQLite» (таблицы слоёв/правил/сегментов/материалов, миграция V26, FHV4, обязательная актуализация всех пользовательских баз) отклонён. Эталон читается живьём из managed `.rvt` при синхронизации (`ExtractSingleSystemType` — тот же код, что строит снапшот для хэша). Обоснование:

- БД отвечает «что и с чем связано и устарело ли» (маркер версии), мини-проект — «какие значения записать». Дублирование не нужно.
- UI-редактор трассировки отменён: редактирование эталона — только в мини-проекте штатными средствами Revit, реимпорт пересчитывает снимок и версию.
- Свойства элемента каталога показывают параметры (уже есть) — слои/трассировку куратор смотрит в самом мини-проекте.
- Стоимость — `OpenDocumentFile` (~1-2 сек) на мини-проект за вызов; одно открытие переиспользуется на все типы одного элемента каталога.

### 3. Хэш FHV3 заморожен; sync-поля — hash-neutral

В хэш системных НЕ добавляются: таблицы размеров сегментов, свойства материалов, `StructuralMaterialIndex`, `EndCap`, `OpeningWrapping`, по-слойные флаги огибания. Эти данные синхронизируются, но в каноническую строку не входят (hasher читает явный список полей — новые поля снапшота помечены как sync-only). Иначе потребовался бы FHV4 + critical-актуализация всех баз + bump min_plugin_version. Копилка пробелов хэша — Issue #179 (там же: «Имя типа» в хэше системных — rename-invariance как #126 для loadable предстоит).

### 4. Маркер версии на ElementType; stale-семантика по типам

- Та же ES-схема `SmartCon_FamilyVersion_v1` (ADR-030), но носитель — `ElementType` проекта. `RevitFamilyVersionStore` обобщён (`IFamilyVersionStore` + `ISystemTypeVersionStore`, один singleton).
- Системный элемент каталога = N типов. Вердикт элемента агрегируется из маркеров его типов, присутствующих в проекте: **stale, если ЛЮБОЙ тип без маркера или с несовпадением** (чистая логика `SystemTypeStaleLogic` в Core). Тип не загружен в проект — не участвует (как unloadable семейство).
- Тип без маркера = stale (`NoEntityStorage`, parity с loadable Issue #69). Осознанно: все legacy-типы до фичи — без маркеров, первый «Проверить» честно покажет их устаревшими.
- Обновление фитинга НЕ делает тип трубы устаревшим: правило ссылается на фитинг по имени, фитинг живёт своим loadable stale-циклом.

### 5. Fast-path по маркеру при размещении

DnD/«Разместить тип» не открывают мини-проект, если маркер типа совпадает с каталогом (та же логика `SystemTypeStaleLogic.ComputeReason`, что и у stale-детектора) — размещение мгновенное, как раньше. Иначе — sync, затем размещение уже обновлённого типа. После успешного размещения запись элемента в stale-снапшоте снимается (`MarkUpdated`), как у loadable.

### 6. Зависимости разрешаются поимённо, ничего не копируется

| Зависимость | Правило |
|---|---|
| Материал | По имени. Есть — полное обновление (графика, appearance через `AppearanceAssetEditScope`, физика/теплотехника через `PropertySetElement`) с отсоединением от общих ассетов (shared appearance/PSE сначала `Duplicate`, чтобы не задеть чужие материалы). Нет — создаётся дубликатом прототипа с asset. Ключевые слова недоступны API (вне скоупа). Отсутствующий ассет в эталоне НЕ очищает целевой (асимметрия осознанная). Материалы никогда не копируются между документами (Revit 2024+ гарантированно дублирует). |
| Сегмент | По имени. Есть — таблица размеров к эталону: добавление/коррекция всегда; удаление — только неиспользуемых размеров и только pipe-сегментов (usage через `RBS_PIPE_SEGMENT_PARAM`+диаметр; для duct usage API не проверить — не трогаем, not-converged); последний размер не удаляем. Нет — `PipeSegment.Create` + `PipeScheduleType.Create` (combo-уникальность material+schedule ловится). Создание duct-сегментов API не предоставляет — Warn + skip правила. |
| Фитинги | Обычные loadable семейства каталога. Есть в проекте по `"{Family}:{Type}"` — используется; нет — догружается из каталога; нет в каталоге — правило пропускается, Warn, тип грузится в остальном полностью. |
| Правила трассировки | Перестраиваются по эталону в порядке правил, группы отсутствующие в эталоне очищаются. Группа Segments никогда не пустеет (если ни один сегмент не резолвится — существующие правила сохраняются + Warn, иначе тип невалиден). «No part» правила (`MEPPartId = InvalidElementId`, сварные системы) — легальный контент, round-trip как есть, НЕ считаются расхождением. |
| Слои конструкций | Полная замена `CompoundStructure`: слои в эталонном порядке (материалы по имени), shell-границы ПОСЛЕ слоёв, variable layer, `StructuralMaterialIndex` точный (чек-бокс «Материал несущих конструкций»), `EndCap`/`OpeningWrapping` + по-слойные `LayerCapFlag`/`ParticipatesInWrapping`. Невалидная структура отклоняется без изменения типа (rejection-safe). `EndCap=NoEndCap` обязателен для не-стен. Вертикально-составные стены — known limitation (API не читает их слои). |

Не приведённые к эталону остатки (используемые размеры, нерезолвленные правила) — счётчик not-converged в статусной строке + Warn[Action] в журнале, без новых диалогов.

### 7. Транзакционная модель

- **Одна транзакция на тип**: создание + параметры + сегменты + материалы + структура + правила + ES-маркер (inline `WriteEntityToElement`) = одна точка отмены на тип.
- **LoadFamily фитингов — строго ДО транзакции**: Revit запрещает `LoadFamily` в modifiable document (`InvalidOperationException`). Следствие задокументировано: при откате sync-транзакции загруженный фитинг остаётся в проекте без правила — приемлемо (переиспользуется следующим прогоном, имеет свой stale-цикл).
- Внутри sync-транзакции `AppearanceAssetEditScope` обязателен открытой транзакции — она есть.

### 8. Коллизия имён с шаблоном при staging мини-проекта (критичный баг ручного теста)

`NewProjectDocument` создаёт мини-проект из дефолтного шаблона, где уже есть типы («Стена 1»). Экспериментально доказано: `CopyElements` при коллизии **копирует входящий тип с авторенеймом** («Стена 2»), а НЕ пропускает его (вопреки ожиданию от `UseDestinationTypes`). Мини-проект получал тип под чужим именем → каталог наследовал «Стена 2» → sync создавал новый тип вместо обновления; хэш менялся с именем → ломался дедуп.

Удалить шаблонный тип заранее нельзя: Revit запрещает удалять **последний тип системной семьи**, причём при копировании Revit ремапит семью типа стены в каноническую «Basic Wall», так что переименованный тип остаётся последним в своей исходной семье. Отказ в UI-сессии = **модальный диалог** (зависание batch-импорта), в headless = **молчаливый `Commit() == RolledBack` без исключения** (системный пробел `RevitTransactionService` — Issue #178).

Решение (`TemplateCollisionResolver`): конфликтующие шаблонные типы **переименовываются** в `zzSmartConTemplate_*` до копирования и **осознанно остаются** в мини-проекте. Безвредны: списки типов каталога строятся из размещённых инстансов (у остатка их нет), sync матчится по имени (префикс не совпадёт), hash-актуализация режет типы до `family_types`.

### 9. Маркеры после «Импорта активного файла»

Типы активного проекта — авторитетный источник только что сохранённой версии → сразу помечаются (`IFamilyVersionWriter.WriteSystemTypeMarkerAsync` по UniqueId, аналог `LoadableMarkerLogic` #84 для loadable). Следующий «Проверить» не флагает их stale.

### 10. UI без новых сущностей

- «Загрузить в проект» для системных: на семействе (все типы, одно открытие мини-проекта) и на типе (один). Попутно починен сломанный путь (раньше вёл в loadable-flow `.rfa`).
- «Проверить»/«Обновить» — полный parity с loadable: те же бейджи, roll-up ⚠, динамическое меню. Для системных «Обновить» — **плоская команда без подменю** (семантика одна — эталон; «Сохранить параметры» не существует).
- Пакетное обновление категории: прогресс «N из M: имя» в статусной строке (`StaleCheckMessage` наконец привязан в XAML; во время батча `StatusMessage` скрывается во избежание наложения).
- Счётчик «не приведено к эталону: N» в статусной строке.

## Классы поведения категорий (покрытие)

1. **MEP с трассировкой** (трубы, гибкие трубы, воздуховоды, гибкие воздуховоды, короба, лотки): параметры + сегменты + материалы + правила + фитинги.
2. **Слоистые** (стены, перекрытия, крыши, потолки): параметры + compound structure.
3. **Простые типы** (лестницы, ограждения, изоляция труб/воздуховодов): только параметры — покрыты скелетом.

## Верифицированные ловушки Revit API (все доказаны интеграционными тестами в реальном Revit)

1. `CopyElements` при коллизии имён копирует с авторенеймом даже с `UseDestinationTypes`.
2. Удаление последнего типа системной семьи запрещено; `Transaction.Commit()` при этом возвращает `RolledBack` **без исключения** (#178), в UI-сессии — модальный диалог.
3. При копировании типа стены между документами Revit ремапит `FamilyName` в каноническую «Basic Wall».
4. `LoadFamily` запрещён при открытой транзакции.
5. `Parameter.ClearValue()` работает только на shared-параметрах (fallback: `Set("")` для строк).
6. Параметры огибания (`WRAPPING_AT_*`) существуют не во всех версиях; современный источник — `CompoundStructure.EndCap/OpeningWrapping` (+shell-слои обязательны для их наличия).
7. `Segment.RemoveSize` бросает только на последнем размере; usage размера Revit не проверяет — проверяем сами (pipe-only).
8. `PipeScheduleType : ElementType` — её собственный Id идёт в `PipeSegment.Create` (форумный сниппет с `GetTypeId()` — ложный).
9. Материалы между проектами не копируем никогда (Revit 2024+ дублирует при совпадении имён).
10. API-созданный материал не имеет appearance asset → создание через `Duplicate()` прототипа.

## Consequences

**Положительные:**
- Системные типы обновляются на месте, экземпляры подхватывают; ноль дубликатов; одна точка отмены на тип.
- Stale/«Проверить»/«Обновить» для системных — полный parity с loadable на существующей инфраструктуре.
- Покрытие интеграционными тестами на границе Revit API (62 теста, R25+R21): sync параметров/структуры/трассировки, коллизия имён, маркеры, no-part правила, rejection-path.

**Отрицательные/риски:**
- Открытие мини-проекта при sync (~1-2 сек на элемент каталога; батч переиспользует одно открытие).
- Каталог всегда прав: локальные правки типов перезаписываются без предупреждения (зафиксировано владельцем продукта).
- Остаточные `zzSmartConTemplate_*` типы в мини-проектах при коллизии с шаблоном — косметика, в каталог не попадают.
- Материал существующего сегмента и спецификация не корректируются (нет API) — only sizes + новые сегменты.

**Out of scope:** UI-редактор трассировки; валидация семейств при импорте (будущий модуль); транзитивное устаревание типа от фитинга; ключевые слова материалов; FHV4 (Issue #179); «Сохранить параметры» для системных.
