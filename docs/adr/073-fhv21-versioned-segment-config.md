# ADR-073: FHV21 — сегментная конфигурация трубы как версионный контент мини-проекта

**Date:** 2026-09-01
**Status:** accepted (решение владельца 2026-09-01: «мини-проект отвечает реально за трубу, вкладка — только за трассировку»; реализовано и прошло gate-валидацию 2026-09-01, ручной стресс-тест владельца подтвердил)
**Related:** ADR-072 (manual miniproject staging / routing as catalog data), ADR-071 (content hash hierarchy), ADR-061 (system family sync), ADR-054 (actualization engine), ADR-055 (family facts / connector_shape), Issue #254

## 1. Context

ADR-072 (World B) вывел трассировку из content-хэша: правила фитингов — это связи
семейств каталога (item-level, V37), а не содержимое файла. Вкладка «Трассировка»
редактировала их на месте, включая строку «Сегменты» с её диапазонами размеров.

Стресс-тест владельца 2026-09-01 выявил концептуальный изъян этого решения:

1. **Диапазоны сегментов — это конфигурация самой трубы, а не связь семейств.**
   Изменение верхнего диапазона сегмента в мини-проекте не меняло хэш (диапазоны
   жили вне хэша, в item-таблицах) → переимпорт давал фантомный «Дубликат», хотя
   труба реально изменилась.
2. **Откат версии не восстанавливал конфигурацию сегментов.** Item-level хранилище
   едино для всех версий: активировав v1 после v2 (где добавили сегмент), пользователь
   видел сегменты v2.
3. **Промежуточное решение (редактируемая строка Segments + промпт расхождения
   мини↔каталог)** было опровергнуто владельцем в ходе обсуждения мульти-сегментного
   кейса: два владельца одних данных = вечный источник рассинхрона.

Решение владельца: **«мини-проект отвечает реально за трубу, вкладка — только за
трассировку»**. Сегменты (сущности: материал, спецификация, размеры), их набор,
диапазоны правил и порядок — версионный контент мини-проекта. Вкладка владеет только
фитингами, их критериями и preferred junction.

## 2. Decision

### 2.1 Разделение владения (итоговая матрица)

| Данные | Владелец | Хранилище | В хэше? |
|---|---|---|---|
| Сущности сегментов (материал, спецификация, размеры) | Мини-проект | `family_segment_sizes` (V36, per-version) | Да (SEGMENTS) |
| Набор сегментов типа, их диапазоны Мин/Макс, порядок | Мини-проект | `family_segment_rules` (V38, per-version) | **Да (FHV21)** |
| Фитинги + их критерии | Вкладка «Трассировка» | `item_routing_rules` (V37, item-level) | Нет (World B) |
| Preferred junction | Вкладка «Трассировка» | `item_routing_type_settings` (V37) | Нет (World B) |

### 2.2 Хэш (FHV21)

- `SegmentSnapshot` получил `RuleMinSizeFeet` / `RuleMaxSizeFeet` (nullable);
  экстрактор читает `PrimarySizeCriterion` правил сегментов из
  `RoutingPreferenceManager`.
- `BuildSegmentsSubstring` пишет диапазон после Roughness (`-` = unrestricted);
  META-префикс системной секции FHV10→FHV11; `FamilyContentHashFormat.CurrentVersion = 21`.
- Изменение диапазона в мини меняет хэш → форк новой версии («Дубликат» ушёл).
  Golden-тест FHV11 + тест «диапазон меняет хэш» фиксируют контракт.

### 2.3 Per-version хранилище (V38)

Таблица `family_segment_rules` (catalog_version_id, family_key, type_name,
rule_order, segment_name, min/max_size_feet NULL = unrestricted, description),
FK `ON DELETE CASCADE`, миграция `MigrateV38Async`. Каждая версия хранит СВОЮ
конфигурацию — откат восстанавливает диапазоны активированной версии.
Писатели: `SegmentRuleWriter` (импорт, оба executor'а) +
`RoutingBackfillActualizationTask` (все варианты, включая архивные) +
`SegmentRulesActualizationTask` (`segment-rules-v1`, optional, Order 76 —
backfill из мини для legacy-версий). `HashFormatActualizationTask` —
`hash-v21` (critical): все FHV≤20-строки pending.

### 2.4 Читатели — единая композиция

`SegmentRuleComposition` (Core): фитинг-группы — из item-канала, сегментная
группа — из per-version таблицы активной версии; legacy-fallback на stored
Segments-строки, пока версия не backfill'нута. Потребители: редактор
(`CatalogRoutingEditorService.LoadAsync`), sync (`SystemTypeSyncService.SubstituteRoutingFromDb`),
обе drift-пробы (`RoutingDriftProbe`, `StaleDetector`). Import-time подмена
(`FamilyImportPreparationService`) подменяет только фитинг-группы — сегментные
правила мини остаются в снапшоте и попадают в хэш.

### 2.5 UI

- Строка «Сегменты» во вкладке — **read-only view** реального критерия каждого
  правила (объясняет размеры в dropdown'ах фитингов). Редактирование — только
  в мини-проекте. Дескриптор: `IsSegmentRow: true, IsReadOnly: true`.
- `TryToRecords` пропускает read-only группы; `SaveAsync` не пишет сегментную
  группу в item-таблицы (legacy-строки сохраняются верbatim). Латентный баг
  потери `PrimarySizeCriterion` при любом save устранён конструкцией.
- Промпт расхождения мини↔каталог **удалён** за ненадобностью (один владелец —
  нечему расходиться).
- Откат версии (`MakeActiveAsync`) перезагружает вкладку Трассировка вживую
  (наряду с Attributes и Assets) — строка сегментов показывает конфигурацию
  активированной версии без переоткрытия окна.

### 2.6 Фильтры пикера по форме коннекторов (тот же стресс-тест)

Факт `connector_shape` (битмаска Round=1, Rectangular=2, Oval=4, ADR-055)
используется тремя фильтрами пикера деталей:

1. **Host-фильтр (баг 8):** кандидат делит хотя бы один бит с формой хост-типа
   (круглый гибкий воздуховод не предлагает прямоугольные фитинги).
2. **`RequiredConnectorShapeMask`:** строки переходов переменной формы
   (круг↔прямоуг., прямоуг.↔овал, овал↔круг — duct manager + flex duct param)
   требуют ВСЕ биты маски — чисто прямоугольный переход не подходит строке
   «Переход с круглого на прямоугольный».
3. **`ExcludeMultiShapeParts`:** обычная строка «Переходы» — только одноформенные
   детали (`m & (m-1) = 0`); мультиформенные живут в своих строках.

Кандидаты без факта (неактуализированная БД) проходят — деградация к legacy-
поведению вместо пустого пикера; `segment-rules-v1`/`family-facts-v1` дозаполняют.

Отображение факта в шапке свойств локализовано (`ConnectorShapeLabelMap`:
«Круглый и Прямоугольный», никаких «Round+Rectangular»); маска 0 (семейство без
коннекторов) читается как «Нет коннекторов». Строка фактов шапки переносится
(WrapPanel) — ширина окна не меняется.

## 3. Consequences

**Положительные:**
- Один владелец каждых данных: нет канала рассинхрона сегментов; промпт не нужен.
- Откат версии семантически полон: восстанавливает и сегментную конфигурацию.
- Хэш видит реальное изменение трубы (диапазон) — фантомные «Дубликат» устранены.
- Пикер никогда не предлагает деталь, которую Revit отвергнет при sync.

**Издержки:**
- Изменение диапазона сегмента требует мини-проекта (вкладка — read-only view) —
  осознанное решение владельца: диапазон = состояние трубы.
- `family_segment_rules` добавляет третий per-version routing-канал; единая
  композиция (`SegmentRuleComposition`) скрывает это от читателей.
- Известный осознанный edge: `Compose` не отличает «легитимно пустую сегментную
  конфигурацию» от «не backfill'нут» — pipe-версия без per-version строк читает
  legacy-строки. Практически недостижимо (Revit требует ≥1 сегментное правило
  на тип трубы); задокументировано в репозитории.
