# ADR-052: Гашение смещения сети длиной трубы (per-level absorption)

**Date:** 2026-07-19 (rev. 2026-07-20 — per-level модель заменила eager-обход поддерева)  
**Status:** accepted  
**Related:** ADR-003 (TransactionGroup), ADR-009 (Vec3 в Core), ADR-043 (PipeConnect модальность)

## Context

При подключении уровня сети в PipeConnect (кнопки `+` / «Подключить всё») элемент
отсоединялся от сети, сдвигался как жёсткое тело на вектор выравнивания `v` и
переподключался. На следующем уровне то же повторялось для его соседей — смещение
протаскивалось через весь граф: подключение одного семейства со смещением 20 мм
сдвигало **всю систему** (например, отопление здания) на 20 мм. Физически такая
корректировка выполняется изменением длины одной трубы, а не переносом всей сети.

Ограничения Revit API (Exa-исследование: Autodesk forum 6857472, The Building
Coder rolling offset, revitapidocs `Pipe.Create`):

- Длина трубы меняется только присваиванием новой кривой:
  `((LocationCurve)pipe.Location).Curve = Line.CreateBound(p0, p1)` —
  `LocationCurve.Length` read-only.
- Жёсткий минимум длины MEPCurve — 1/10" (~2.54 мм); ниже — `ArgumentException`.

### Почему eager-модель отвергнута (3 полевых бага за один день)

Первая реализация распространяла смещение вглубь поддерева сети eagerly
(планировщик `DisplacementAbsorptionPlanner` + `BuildAbsorptionSubtree`):

1. **Весь узел двигался за один уровень** (`moves=21`) — ветки без поглощающих
   труб сдвигались «впрок», ломая поуровневый UX.
2. **Не-трубопроводные коннекторы** (электрика на насосе) попадали в план и
   теряли соединения («connector lost»).
3. **Асимметрия:** уровень 6 подключал сразу 9 элементов (включая трубы уровней
   12–13, которым потом «нечего было подключать»), а откат шёл поэлементно.
   Бухгалтерия откатов (многоуровневый restore, ConnectedLevel) разрасталась
   без надежды на консистентность.

## Decision

### Per-level модель: труба гасит смещение на СВОЁМ уровне

Смещение распространяется по уровням классическим потоком — по одному элементу
за инкремент (фитинги и семейства двигаются жёстко, как раньше). Единственное
отличие: когда инкремент доходит до элемента, который **сам является прямой
трубой**, и его выравнивание — чистая трансляция, труба **меняет длину вместо
перемещения**:

- ближний к родителю конец `LocationCurve` следует за вектором выравнивания `v`
  (совпадает с коннектором родителя),
- дальний конец получает только непоглощённый остаток `v - axis·absorbed`
  (при полном поглощении — ноль, propagation останавливается).

Остаток (частичное поглощение, перпендикулярная составляющая) обрабатывает
следующий уровень классически. Итоговая геометрия после обработки всех уровней
совпадает с eager-моделью, но достигается поэлементно — вперёд и назад
симметрично: один уровень = один элемент = одна undo-операция. Никакого обхода
поддерева, никаких кросс-уровневых снапшотов.

Математика (`PipeLengthAbsorber.Compute`, pure Core, Vec3):

```
axis     = normalize(far - near)      // near — конец ближе к коннектору родителя
axial    = dot(v, axis)
absorbed = axial > 0 ? min(axial, max(0, length - minPipeLength)) : axial
nearDelta = v
farDelta  = v - axis * absorbed
```

- Укорочение ограничено минимальной монтажной длиной; удлинение — нет.
- Перпендикулярная труба вырождается в чистую трансляцию (`absorbed ≈ 0`).
- Поворот в выравнивании → классический rigid align (труба поворот не гасит).

### Минимальная длина трубы — 100 мм (хардкод)

`PipeAbsorption.MinPipeLengthMm = 100.0` в `SmartCon.Core/Constants.cs`,
`MinPipeLengthFt = 100 / 304.8` (I-02: Core работает в decimal feet, конвертация
через точный фактор 1 ft = 304.8 mm). Жёсткий минимум Revit ~2.5 мм непригоден
монтажно; практика (Victaulic Field Installation Handbook, сварные/резьбовые
вставки) — короткие вставки от ~100 мм. Хардкод вместо настройки — осознанное
упрощение (не проверять частные случаи «труба заходит внутрь другого семейства»).

### Архитектура по Dependency Rule

| Слой | Артефакт | Роль |
|---|---|---|
| Core | `PipeLengthAbsorber` (Math, Vec3) | Pure math, 9 юнит-тестов |
| Core | `PipeAdjustOp` (Models) | Дельты концов кривой; id сырым `long` — тестируемость |
| Core | `PipeAbsorption` (Constants) | Лимит 100 мм (SI) + футы |
| PipeConnect | `ChainOperationHandler.TryAlignPipeByLength` | Перехват в `ProcessIncrementElement` внутри существующей `ITransactionGroupSession` (I-03/I-04) |

Точка интеграции одна: в `ProcessIncrementElement` вместо `AlignElement`
вызывается `TryAlignPipeByLength`; если элемент не труба, поворот обязателен или
установка кривой упала — классический `AlignElement`. Дальний конец трубы
переподключается не сразу, а на уровне downstream-соседа обычным потоком
(`FindEdgeToParent` → align → `ReconnectIncrementElement`) — поэтому
`DecrementLevel` остаётся поуровневым без изменений.

## Consequences

**Плюсы:**
- Сеть больше не сдвигается целиком: смещение останавливается на первой трубе
  вдоль оси; остальная сеть за трубой не двигается.
- Полная симметрия increment/decrement — откат поуровневый, как до фичи.
- Электрика и прочие домены не затрагиваются (обработка только своего элемента).
- Кодовая база прощё: нет планировщика поддерева, нет ConnectedLevel, нет
  многоуровневых откатов.

**Минусы / ограничения:**
- Повороты не гасятся (физически невозможно длиной трубы) — rigid align.
- FlexPipe и непрямые кривые не участвуют (только `Line`).
- Гашение применяется на уровнях сети; начальное выравнивание самого dynamic
  элемента не меняется (он отсоединяется от сети по дизайну сессии).
