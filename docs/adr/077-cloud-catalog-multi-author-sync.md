# ADR-077: Cloud Catalog Multi-Author Sync — pull-before-push с per-item optimistic concurrency

**Date:** 2026-08-25  
**Status:** proposed  
**Related:** ADR-075 (Cloud Architecture), ADR-076 (Security), ADR-015 (single-writer SMB — контраст), ADR-022 (роли), ADR-040 (OverwriteCurrent), ADR-041 (Active Version Management)  
**Детальный план:** [`docs/family-manager/02-plans/cloud-catalog-master-plan.md`](../family-manager/02-plans/cloud-catalog-master-plan.md)

## Context

В локальных/SMB-каталогах concurrent-запись решает SQLite single-writer
(ADR-015): 2–3 BIM-мастера правят одну базу, гонки гасятся busy_timeout.
В облачном каталоге каждый автор правит **свою локальную копию** и публикует
на сервер — single-writer не работает, нужна явная модель совместной работы.

Требования владельца (2026-08-25): «один автор опубликовал радиатор новой
версии, другой — вентилятор, оба изменения улетели без конфликтов, каждый при
синхронизации получил изменения друг друга». Аналогия владельца — кнопка Revit
«Синхронизировать с файлом хранилища». Редакторов на каталог ожидается 2–3.

Отклонённые альтернативы:

- **Real-time co-editing (CRDT/OT)** — безумная сложность для каталогов,
  меняющихся раз в дни; требует постоянного соединения, ломает offline-first.
- **Checkout-локи семейств** («занял радиатор на редактирование») — требует
  онлайна для начала работы, противоречит offline-first; UX-бюрократия для
  2–3 человек.
- **Last-writer-wins на весь каталог** (снапшот затирает чужие изменения) —
  потеря данных при одновременной публикации. Недопустимо.
- **Server-side merge двух манифестов** — сервер не может судить о семантике
  конфликта одного семейства; переносит ответственность с автора на алгоритм.

## Decision

### 1. Роли публикации

`Owner` и `Editor` (ADR-076 §1) могут публиковать. `Subscriber` — никогда.
Owner дополнительно управляет редакторами и ключами. Передача ownership —
явная операция (по образцу локального `TransferOwnershipAsync`, ADR-022).

### 2. Pull-before-push (обязательный порядок)

Клиентская команда **«Синхронизировать»** для опубликованной базы всегда
выполняет: (1) pull — применить к локальной копии все publish points новее
`lastSyncedPublishSeq`; (2) push — отправить локальные изменения. Команды
«только push» в UI нет. Это буквально модель «Синхронизировать с файлом
хранилища» из Revit worksharing.

### 3. Per-item optimistic concurrency

Сервер хранит per-item курсор: `catalog_items_mirror(item_id,
last_modified_publish_seq, last_modified_by)`. Push — это **дельта**, а не
полный снапшот:

```
POST /catalogs/{id}/publish
{
  "basePublishSeq": 42,                // на чём основана дельта
  "changes": [
    { "op": "upsert-item", "item": {...}, "versions": [...] },
    { "op": "upsert-version", "itemId": ..., "version": {...} },
    { "op": "deprecate-item", "itemId": ... },
    { "op": "delete-version", "itemId": ..., "versionLabel": "v2" }
  ]
}
```

Сервер для каждого изменённого `itemId` проверяет:
`last_modified_publish_seq(item) <= basePublishSeq` → применить.
Иначе — **409 Conflict** с машиночитаемым списком конфликтных items
(`{itemId, name, serverModifiedBy, serverPublishSeq}`).

- Изменения в **разных** семействах → никогда не конфликтуют (сценарий
  «радиатор + вентилятор» владельца — норма, 99% случаев при 2–3 редакторах).
- Неконфликтная часть дельты **не применяется частично**: publish атомарен
  (одна PG-транзакция) — либо весь, либо 409. Иначе автор не сможет рассуждать
  о состоянии каталога.

### 3a. Серверная дедупликация при publish

Per-item курсоры не ловят параллельное создание **разными** авторами item'ов с
одинаковым контентом (новые guid — конфликта нет, а дубль есть; локально это
известная боль `FindByNormalizedNameAsync`). Поэтому publish-валидация
включает: upsert-version с `content_hash`, уже существующим в каталоге под
**другим** item_id, → **422** с машиночитаемым `duplicateOfItemId` (индекс
`item_versions_mirror(catalog_id, content_hash)`). Клиент показывает:
«Семейство уже опубликовал {user} в публикации №{seq} как {name}»; автор либо
удаляет локальный дубль (cross-name ⚠ флоу ADR-049), либо согласовывает.
Auto-merge на сервере запрещён (сервер не судит семантику).

### 3b. Иммутабельность опубликованных версий (OverwriteCurrent через облако)

Локальный OverwriteCurrent (ADR-040) перезаписывает файл той же метки. Через
облако это ломает подписчиков: их ссылки (stale-маркеры, presence, загруженные
типы) указывают на старый контент под тем же label. Поэтому сервер
**отклоняет** upsert-version с существующим `(itemId, versionLabel)` и
отличающимся `content_hash` → **422** «опубликованная версия иммутабельна —
создайте новую версию (vN+1)». Клиентский publish-сервис обязан до отправки
конвертировать локальные OverwriteCurrent-изменения в новые version labels
(правило действует и на `OverwriteCurrent`, выполненный после первой
публикации).

### 3c. Hash epoch: миграция формата хэша (FHV11 → FHV12…)

Правило §3b имеет **единственное исключение** — смена формата хэша: при ней
`content_hash` каждой версии меняется при неизменном контенте и неизменном
label (локально это critical-задача actualization, ADR-054/056/069; формат
менялся уже 11 раз — recurring-процесс, не гипотетика). Без явной механики
каталог не смог бы мигрировать формат, не ломая item id у подписчиков.

**Операция `rehash`:** publish point может быть помечен `kind: "rehash"` и
тогда: (а) дельта состоит только из `rehash-version` операций — обновление
`content_hash` существующего `(itemId, label)` с **сохранением item id** и без
новых файлов (sha256 файлов не меняются!); (б) publish point обязан покрывать
ВСЕ items каталога (полный пересчёт, как local actualization); (в) `§3b` для
rehash-операций не применяется, но per-item курсоры (§3) — применяются;
(г) `hashFormatVersion` каталога поднимается атомарно с publish point;
(д) `minPluginVersion` каталога поднимается до версии плагина, понимающей
новый формат → подписчики на старом плагине получают E7-гейт (баннер
«обновите SmartCon», копия остаётся на старом publish point и работает).

При rehash-commit сервер обновляет `item_versions_mirror.content_hash` под
новый формат (иначе дедуп-валидация §3a сломается на следующем обычном
publish), сохраняя `published_by`/даты исходных версий. Подписчик применяет
rehash-манифест как обычный (applier обновляет `content_hash`/
`hash_format_version` строк, файлы не трогает). Локальный ES-маркер
`SmartCon_FamilyVersion_v1` не зависит от формата хэша (хранит label), stale
detection продолжает работать.

### 4. Разрешение конфликта — на клиенте, явно

При 409 клиент: (1) pull (получает чужую версию семейства); (2) показывает
**диалог конфликта** по каждому item: «Ваша версия (неопубликованная) /
Версия {user} из публикации №{seq}» → выбор: **[Взять серверную]** (мои
локальные правки item отбрасываются), **[Опубликовать мою поверх]** (моя
версия становится следующей `vN`), **[Оставить обе]** (моя версия публикуется
как отдельный item с суффиксом имени — для осознанного форка).

По умолчанию подсвечивается «Опубликовать мою поверх» (самый частый честный
сценарий: оба автора улучшали одно семейство последовательно).

**Кейс undelete:** если конфликт вызван тем, что item **удалён** другим автором
(tombstone), вариант «Опубликовать мою поверх» недоступен — моя версия
публикуется только как **новый item** (новый item_id; tombstone исходного
остаётся в истории). Воскрешения item под старым id нет: подписчики уже
применили удаление, и возврат того же id создал бы рассинхрон их копий.

**Кейс metadata-конфликта:** диалог 409 показывает число изменённых
категорий/атрибутов/правил у каждой стороны (считается при pull), чтобы выбор
«публиковать поверх» был информированным — см. Consequences о data-loss window.

### 5. Метки версий при гонке

`version_label` (`v1`, `v2`, …) вычисляется клиентом
(`ComputeNextVersionLabelAsync`). При конфликте и выборе «мою поверх» клиент
**переназначает метку** на актуальный next после pull (чужая `v3` → моя станет
`v4`). Локальная запись версии обновляет label до повторного push — метки
монотонны и уникальны per item глобально, потому что финальное слово всегда за
сервером (он отклонит дубль UNIQUE(item,label) как конфликт).

### 6. Удаления и tombstones

Удаление item/версии автором — операция дельты (`delete-*`), на сервере
становится **tombstone** в publish point (манифест хранит `removed: [...]`).
Подписчики при pull помечают item удалённым в локальной копии (purge файлов —
по подтверждению, как в existing purge-флоу). Загруженные в проекты Revit
семейства не затрагиваются никогда. Dependency Guard (ADR-067) проверяется
**локально до push**; сервер дополнительно валидирует ссылки дельты
(серверная копия family_dependencies в схеме есть) и отклоняет publish,
ломающий чужие ссылки, с 422.

**Исключение для store-каталогов (C7):** `delete-item/delete-version` при
живых entitlements (проданные семейства) запрещён сервером (422) — проданное
не удаляется никогда, только Deprecated. Это второй «guard» после Dependency
Guard, той же природы.

### 7. Что не поддерживается

- Одновременное редактирование **структуры категорий/атрибутов/правил**
  (metadata-слой) двумя редакторами: metadata-секция манифеста —
  last-writer-wins **целиком** с тем же baseSeq-гейтом и явным 409
  («метаданные изменил {user}, синхронизируйтесь»). Редакторы договариваются
  вне системы; авто-merge деревьев категорий — non-goal.
- Переименование item одним редактором + новая версия другим — трактуется как
  конфликт item (любое изменение item → тот же курсор).

## Consequences

- Нормальный сценарий 2–3 редакторов не требует ни локов, ни онлайна до
  момента синхронизации: правки локальны, publish — транзакция.
- Конфликт — редкое, явное, разрешимое событие с человекочитаемым UX
  (как «своя/чужая версия» в Revit worksharing).
- Атомарность publish + tombstones дают воспроизводимость: любой publish
  point — полное консистентное состояние каталога.
- Known limitation: **metadata LWW data-loss window** — после разрешения
  metadata-конфликта (§7) повторный publish затирает metadata первого автора
  целиком; тот узнаёт об этом только при следующем pull (уведомлений нет).
  Смягчение: диалог 409 показывает объём чужих metadata-изменений; полноценный
  merge деревьев — non-goal.
- Known limitation: серия 409 подряд при активной парной работе над одним
  семейством решается социально (договориться) — система честно сообщает, но
  не сериализует авторов принудительно.
- Known limitation: `basePublishSeq` устаревает между pull и push в пределах
  одной команды (гонка в миллисекунды) — 409 обрабатывается как обычный
  конфликт-флоу (повторный цикл pull→push), автоматически один retry без
  диалога, если после pull конфликтов по items нет.

## Verification

- Unit: серверный publish-валидатор (per-item курсоры, атомарность, 409/422,
  дедуп §3a, иммутабельность §3b, rehash-операция §3c), клиентский
  conflict-resolver (переназначение label, три выбора + undelete).
- Интеграция (фаза C4): два клиентских процесса против одного сервера —
  сценарии «разные items», «один item», «metadata-gate», «retry без диалога»,
  «rehash-epoch с сохранением item id».
- Ручной тест владельца: два Revit на двух машинах, роль Owner+Editor.
