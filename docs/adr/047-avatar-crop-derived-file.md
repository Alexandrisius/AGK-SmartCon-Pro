# ADR-047: Avatar Crop — производный файл avatar.png, единая миниатюра 560×420 для аватарки и tooltip

**Date:** 2026-07-16  
**Status:** accepted  
**Related:** Issue #131 (диалог кадрирования аватарки и tooltip-изображения)

## Context

В FamilyManager пользователь прикрепляет к семейству изображения любого разрешения. Аватарка в диалоге свойств (280×210) и превью в tooltip (240×180) показывали **исходный файл как есть** с `Stretch="UniformToFill"` — WPF обрезал его по центру, без контроля со стороны пользователя. Важные части изображения (логотип, центральный объект) обрезались, неподходящие кадры попадали в каталог.

Issue #131 требует: универсальный диалог кадрирования (рамка + зум/пан + затемнение), открывающийся при «Сделать главной» (★) и «Сменить аватарку», и **единую** миниатюру для обоих превью.

Ключевые ограничения:

- Исходные изображения — пользовательские данные; перезаписывать их кропом нельзя (безвозвратная потеря оригинала).
- Managed storage ассетов — append-only по духу (см. ADR-016 для `.rfa`); «мусорные» дубли кропов в списке ассетов нежелательны.
- Аватар обозначает семейство целиком, а не конкретную версию — хранение в per-version папке было бы неверно.
- WPF-типы (`BitmapSource`, `CroppedBitmap`) запрещены в `SmartCon.Core` (I-09), но вся геометрия диалога должна быть unit-тестируемой.

## Decision

### 1. Производный файл `avatar.png` на семейство

Кроп сохраняется как единый производный файл `{db-root}/files/{catalogItemId}/avatar.png`:

- **560×420 PNG** (4:3, 2× supersample для 280×210 @ high-DPI), всегда перезаписывается целиком.
- **Версионно-независим**: аватар представляет семейство, а не версию (лежит в корне family-папки, не в `assets/images/`).
- **Не ассет**: записи в `family_assets` не создаётся — список ассетов не засоряется, `is_primary` остаётся на исходном изображении-источнике.
- **Не подпадает под I-16**: read-only иммутабельность относится к managed `.rfa`; `avatar.png` — перегенерируемый UI-артефакт.

### 2. Инвалидация при смене primary

`IFamilyAssetService.SetPrimaryAssetAsync` **удаляет** `avatar.png` после переключения `is_primary`: производный файл отрендерен из прежнего primary и становится stale. Новый кроп записывается последующим `SaveAvatarAsync`. Это гарантирует отсутствие мусора и рассинхрона (требование из issue).

### 3. Единая цепочка разрешения аватара

`IFamilyAssetService.GetAvatarImagePathAsync(catalogItemId, versionLabel)` — единственная точка:

```
avatar.png (если существует) → primary image asset → null
```

Fallback на primary сохраняет обратную совместимость: семейства, у которых primary был назначен до #131, продолжают показывать его без миграции. Fallback на «первое изображение» (был в `LoadAssetsAsync`) **убран** — иначе «Удалить аватарку» (`ClearAvatarAsync`) немедленно «воскрешал» бы превью первой картинкой.

### 4. Унификация размеров превью

Оба превью (диалог свойств и tooltip) — **280×210** (4:3), источник — один и тот же `avatar.png`. Tooltip увеличен с 240×180 до 280×210; декодирование ограничено `DecodePixelWidth=560` (в т.ч. в `FamilyPropertiesView`, где раньше декодировалось полное разрешение исходника).

### 5. Диалог кадрирования — WPF-free ViewModel + pure math в Core

- `CropViewportMath` (Core, pure static): fit-scale, `MinZoom`, клампы пана/рамки, маппинг экран→пиксели. Инвариант: изображение всегда покрывает рамку 4:3 (400×300 в вьюпорте 600×450) — пустых пикселей в кропе быть не может.
- `CropAvatarViewModel` (FamilyManager) — только `double`-состояние, без WPF-типов → unit-тестируем. Mouse-ввод (wheel-зум вокруг курсора, пан, drag рамки-Thumb, геометрия затемнения `CombinedGeometry Exclude`) — через Behaviors (I-10).
- `IAvatarCropService` (Core-интерфейс) / `WpfAvatarCropService` (FamilyManager): `CroppedBitmap` → `DrawingVisual` с `BitmapScalingMode.HighQuality` → `RenderTargetBitmap` 560×420 → `PngBitmapEncoder`. Декод исходника ограничен 4096px по ширине — «очень большие» изображения не взрывают память; кроп-rect пересчитывается из нативных пикселей в декодированные.

### 6. Точки входа

1. ★ «Сделать главной» — всегда диалог; Apply → `SetPrimaryAssetAsync` (удаляет старый avatar.png) → `SaveAvatarAsync`.
2. «Сменить аватарку» — выбор файла → диалог; Apply → добавление оригинала в ассеты → primary → save; **Cancel — ассет не добавляется**.
3. Первичная загрузка первого изображения (`AddAsset`/`AddFileUnified`, когда Image-ассетов не было) — диалог; Cancel — файл остаётся обычным ассетом. Последующие добавления — без диалога.

### 7. Изменение семантики «Удалить аватарку»

`RemoveAvatar` теперь вызывает `ClearAvatarAsync` (удалить `avatar.png` + сбросить `is_primary`) вместо удаления primary **ассета** с диска. Исходные изображения пользователя сохраняются (их удаление — отдельная кнопка в списке ассетов). Семейства с legacy-primary без `avatar.png` кнопкой «Удалить» также очищаются.

### 8. GIF и прочие форматы

Анимированные GIF кадрируются по первому кадру (как и раньше при отображении). Все поддерживаемые WIC-форматы (png/jpg/bmp/gif/tif) обрабатываются единообразно.

## Consequences

- Пользователь контролирует кадр аватарки; превью в свойствах и tooltip визуально идентичны (один файл, один аспект, один размер).
- Старые данные работают без миграции: primary image остаётся аватаром до первого перекропа.
- Повторные кропы не плодят файлы: один `avatar.png`, перезапись, инвалидация при смене primary.
- Любое разрешение источника: от 100×75 (апскейл) до 8000×6000+ (декод-кап 4096 для рендера, 2048 для превью в диалоге).
- Стоимость: +1 файл на семейство (~100-200 КБ PNG); tooltip VM кэширует загруженный bitmap до пересоздания узла дерева (пересоздаётся при `LoadTreeAsync` после закрытия свойств с OK).

## Amendment 2026-07-16 (rev 2) — free-aspect рамка, live-preview, мгновенное обновление превью

Ручное тестирование выявило два недостатка rev 1:

### 1. Stale-изображение при повторном кропе (bug)

`avatar.png` перезаписывается **по тому же пути** → path-string биндинг не изменялся → WPF не пересоздавал `BitmapImage` → аватарка в свойствах менялась только после переоткрытия диалога. Решение:

- Аватарка свойств — `BitmapImage`-свойство `AvatarImage` в `FamilyPropertiesViewModel`, декодируется заново при каждом `LoadAssetsAsync` через общий `AvatarImageLoader` (`IgnoreImageCache`, `DecodePixelWidth=560`).
- `FamilyPropertiesViewModel.AvatarChanged` (event) — вызывается после `SaveAvatarAsync`/`ClearAvatarAsync`; `FamilyManagerMainViewModel.OpenProperties` подписывается и инвалидирует `TooltipViewModel` текущего узла дерева (`Invalidate()` сбрасывает `_loaded`-кэш и перезагружает изображение). Tooltip обновляется мгновенно, без ожидания `LoadTreeAsync` (который к тому же не выполняется при Cancel).

### 2. Свободные пропорции рамки (free aspect)

Для вертикальных изображений рамка 4:3 слишком ограничивала. По best practices (CommunityToolkit `ImageCropper` с `AspectRatio=null`, react-avatar-editor, vue-advanced-cropper):

- Рамка **произвольных пропорций**: 4 угловых resize-хэндла (`CropFrameResizeBehavior` + `CropViewportMath.ResizeFrame`, min 60×60, кламп в image ∩ viewport, противоположный угол закреплён).
- Вывод **всегда** 560×420 (4:3) с **cover-семантикой**: выбранная область масштабируется до заполнения кадра, излишек по длинной оси обрезается по центру (как `Stretch=UniformToFill`). `MinZoom` пересчитывается после каждого resize.
- **Live-preview результата** (140×105) справа в диалоге: `ImageBrush` с `Viewbox` = нормализованная выбранная область + `UniformToFill` — пиксель-в-пиксель та же cover-операция, что и рендерер. Пользователь заранее видит итог с обрезанными полями; подсказка-подпись (`FM_Crop_CoverHint`) объясняет семантику.
- Кнопки диалога приведены к стандарту FamilyManager: **80×28** (`PrimaryButton`/`SecondaryButton`).

## Amendment 2026-07-16 (rev 3) — contain-семантика + фикс дребезга resize

Повторное ручное тестирование:

### 1. Дребезг угловых хэндлов (root cause: bubbling DragDelta)

`Thumb.DragDelta` — **маршрутизируемое bubbling-событие**. Угловые resize-хэндлы вложены в template Thumb'а рамки → их DragDelta всплывал до внешнего Thumb → срабатывал `MoveFrame` (вся рамка, включая противоположный угол, двигалась) **одновременно** с `ResizeFrame` → угол получал двойную дельту → осцилляция/мерцание вокруг курсора. Фикс: в `CropFrameDragBehavior` и `CropFrameResizeBehavior` обрабатывается только `ReferenceEquals(e.OriginalSource, AssociatedObject)`.

### 2. Cover → contain

Пользователь ожидает, что выбранная область (напр. узкая вертикальная полоса) показывается **целиком** («во весь рост»), а cover обрезал её по длинной оси. Семантика рендера изменена на **contain**: вся выбранная область масштабируется в 560×420 целиком, свободные поля остаются прозрачными (PNG alpha; на карточке/в tooltip сквозь них виден фон). Live-preview синхронно переключён на `Stretch="Uniform"` — превью по-прежнему пиксель-в-пиксель совпадает с результатом. WYSIWYG: что выделено — то и в аватарке, без сюрпризов.
