# ADR-074: Комплаенс-проверка каталога по актуальным правилам («Проверить → Правила»)

**Date:** 2026-09-08  
**Status:** accepted  
**Related:** ADR-059 (Import Validation Gate), ADR-030 (Stale Detection v2), ADR-066 §6 (клик-бэйджи #210), Issue #259, #256 (прогресс-бар панели), #180/#185 (контентная верификация)

## Context

Правила валидации (`category_validation_rules`, schema v25) работали только
как **гейт входа** (ADR-059): batch-диалог импорта (forced Skip), смена
категории DnD (`CategoryChangeGateService`), пикер категории в окне свойств.
Существующий каталог по актуальным правилам **не перепроверялся никогда**:
после усиления правил или смены привязок категорий уже импортированные
элементы тихо переставали соответствовать требованиям — уверенность была
«заморожена» на наборе правил момента импорта.

Решение владельца (2026-09-07): команда «Проверить» получает подменю из двух
команд с двумя независимыми логиками — «Актуальность» (существующая
stale-логика, проект vs каталог) и «Правила» (новая комплаенс-проверка,
каталог vs актуальные правила категории).

## Decision

### 1. Две независимые команды, вердикты не смешиваются

`StaleReason` НЕ расширяется значением «RuleViolation». Причины:

- кнопка «Обновить» применяет контент каталога к проекту и нарушение правила
  не исправит — объединённый вердикт заставил бы кнопку врать;
- «Правила» работают **без открытого документа** (pure SQLite + pure
  `IFamilyValidationEngine`) и покрывают элементы, которых в проекте нет;
- стоимость несопоставима: stale ≈ 1.4 с/семейство (EditFamily +
  OpenDocumentFile), комплаенс — миллисекунды/элемент (SELECT из
  `family_data_import_runs` + `extracted_attribute_values` + `family_types`
  и цикл type×rule).

CanExecute «Правил» не требует документа; обе команды разделяют guard
`IsStaleCheckInProgress` и прогресс-бар панели (#256) — параллельные прогоны
исключены, индикация единообразна.

### 2. Сервис поверх готовых швов, без нового движка

`ICatalogComplianceService` (Core-контракт) / `CatalogComplianceService`
(FamilyManager, DI-синглтон) переиспользует офлайн-вход гейта смены категории:
`GetEffectiveRulesAsync(categoryId)` + `ValidateCatalogItemAsync(itemId, rules)`.
Никакого Revit, никакого открытия `.rfa`, схема БД не меняется.

- правила кэшируются **на категорию на прогон** (резолв правил ходит в
  SQLite; контракт «один резолв на категорию» зафиксирован юнит-тестом);
- категория без правил = free pass (семантика гейта импорта), чтение
  экстракции коротко замыкается;
- охват категории = всё поддерево (`ExpandCategorySubtree`, единая семантика
  с «Актуальностью»); синтетический `"__no_category__"` обрабатывается как в
  `StaleDetector.CheckCategoryAsync`;
- per-item изоляция ошибок: битая строка деградирует в `CannotVerify`
  (notice указывает на «Обновить базу»), а не топит весь прогон.

### 3. Вердикты: сессионный снимок без миграции схемы

`CatalogComplianceSnapshot` — in-memory снимок по образцу `FamilyStaleSnapshot`
(ADR-030 D-06): `Pass | Fail | CannotVerify` на элемент, value-equality,
lock-защищённые merge/invalidate. Персистентность вердиктов (+ fingerprint
набора правил) отложена в фазу 2 — для v1 достаточно жизни бэджей в пределах
сессии. Инвалидация:

| Триггер | Механика |
|---|---|
| Сохранение правил/биндингов (редактор категорий, импорт JSON) | сервис сам подписан на `IFamilyManagerMetadataMediator.MetadataChanged` |
| Смена активной БД | `InvalidateCache()` в `OnActiveDatabaseChanged` (вердикты per-DB) |
| «Обновить базу» (actualization бэкафиллит атрибуты) | `InvalidateCache()` после `UpdateAsync`/`EnsureUpToDateAsync` |
| Реимпорт элемента (новая версия прошла гейт на входе) | `InvalidateItems(ids)` в пост-импорт хуке |
| Смена категории элемента (DnD/пикер) | **автоинвалидация при применении**: вердикт хранит `CategoryId` и применяется к листу только при совпадении с текущей категорией — проводка в DnD/свойства не нужна |

Перевалидация — читательская операция: новая версия создаётся ТОЛЬКО
импортом с `IncrementVersion`, автоматических версий от изменения правил нет.

### 4. Бэйджи по канону #210: StatusNotice, не новая ad-hoc иконка

- **Fail** → Error-notice «Не соответствует правилам категории (N нарушений)»
  + guidance «Исправьте семейство и импортируйте новую версию — гейт импорта
  перевалидирует его по действующим правилам»; собственный **красный щит**
  (`ShieldAlertOutline`/`DangerBrush`, `StatusBadgeButton`) у листа и roll-up
  у категории — цвет/иконка отделены от stale-оранжевого;
- **CannotVerify** → Warning-notice «Правила нельзя проверить: нет данных
  атрибутов» — едет на существующем оранжевом треугольнике
  (`HasProblemBadge`), третьей иконки нет;
- отчёт: действие «Открыть отчёт о проверке» в «Деталях статуса» строит
  существующий `ValidationReportViewModel` (тип/атрибут/условие/ожидалось/
  фактически + сводка + копирование) из снимка — диалог не переделывался.
  Смешанный набор действий (update + report) получает нейтральную метку
  сплит-кнопки «Действия» вместо «Обновить».

## Alternatives considered

- **Расширить `StaleReason` значением `RuleViolation`** — отвергнуто: кнопка
  «Обновить» начала бы врать (см. Decision 1), плюс stale-проверка требует
  открытый проект и покрывает только загруженные семейства.
- **Одна объединённая команда «Проверить»** — отвергнута решением владельца:
  две семантики, два покрытия, две стоимости, разные действия лечения.
- **Персистентные вердикты в БД сразу (фаза 2)** — отложено: сессионный
  снимок закрывает сценарий без миграции схемы; персистентность понадобится,
  только если бэджи должны жить между сессиями.
- **Своя иконка/цвет на каждый статус** — отвергнуто каноном #210 («новый
  бэйдж = новая запись StatusNotice»); красный щит добавлен как отдельный
  `StatusBadgeButton`, а не как новый механизм.

## Consequences

- Положительные: уверенность каталога больше не «заморожена» на моменте
  импорта; проверка всего поддерева занимает миллисекунды и доступна офлайн;
  гейт-семантика едина для входа (импорт/DnD) и аудита («Правила»).
- Отрицательные/ограничения: бэйджи живут только в пределах сессии (фаза 2 —
  персистентность + fingerprint набора правил); исправление нарушений —
  ручные версии (возможная политика гашения волны `OverwriteCurrent` —
  решение владельца при внедрении); `StatusMessage`-строки команд — хардкод
  ru (существующий паттерн stale-команд, локализуется отдельной задачей).
- Тесты: 16 сервисных (`CatalogComplianceServiceTests`, реальная цепочка на
  TempCatalogFixture + Moq-контракт кэша правил) + 6 notice-тестов бэджей.
  Интеграционные не требуются — Revit-boundary не изменяется.
